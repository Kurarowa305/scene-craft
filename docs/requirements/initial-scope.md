# scene-craft 初期要件

2026-10-04〜05 の要件整理で合意した初期範囲。2026-10-06 に調査資料から独立した文書へ整理した。ここに記すのは合意済みの要求・制約であり、実装済みという意味ではない。

Blender と Photoshop を使う、一人の背景イラスト制作を支援する。参考調査から編集可能な 3D シーンの作成、レンダー出力までをエージェントが支援し、その後の手作業も制作履歴へ残す。完成作品と制作過程を振り返り、作風の傾向を言語化して次の制作や将来のレビューに活かす。将来は人間の確認・調整を挟みながら工程を連続して進められるようにする。

本書を初期要件の参照元とし、変更には人間との合意と理由の記録を伴う。設計の現在値は [設計資料](../design/README.md)、検討経緯は設計 Issue、開発の進め方は [開発フロー](../agents/development-workflow.md) に置く。用語は [GLOSSARY.md](../../GLOSSARY.md) に従う。

<a id="scope"></a>

## 初期範囲と人間の役割

初期は次の9役割を対象とする。一工程だけに限定する方針は採らない。役割数と独立した実行プロセス数を一致させる必要はなく、実装上の分け方は設計で決める。

1. 参考調査・検討項目の整理
2. シーン計画・制作要素の分解
3. 仮形状・定型モデリング
4. アセット検索・取り込み
5. 周辺整備・植物・小物配置
6. UV・画像テクスチャ適用
7. 空・海・照明・3D の雲の設定
8. レンダー出力・引き渡し
9. 振り返り・作風の言語化

- 工程の進行管理は将来段階とし、初期は人間が工程ごとのエージェントを選んで呼び出す。作品の制作意図・採用済みの結果・制作履歴は次のエージェントへ引き継ぐ。
- 画面レビューは初期対象に含めない。振り返り・作風の言語化は引き続き初期対象とする。
- 初期のエージェントによる制作操作はレンダーファイルの出力までとし、その後の Photoshop 操作はすべて人間が行う。当初選んだレイヤーの名前変更・グループ化の支援も初期対象から外す。レタッチ以降の作業記録を scene-craft に残すことと、振り返り・作風の言語化は引き続き初期対象とする。

<a id="app"></a>

## 利用形態・会話・費用制約

- 初期から scene-craft 専用の会話アプリを作る。手元の PC で起動し、ブラウザから使うローカル Web アプリとする。対象作品を明示して工程別のエージェントを呼び出し、採用や記録を指示する。初期画面には作品一覧、作品ごとの会話、生成物・編集案の確認と採否、制作履歴と手作業の登録、作風・制作方針の参照と版の選択を含める。配置や見た目は UI 設計で決める。
- LLM 呼び出しは ChatGPT Pro の契約内に収め、API 従量課金は許容しない。利用者が検証に使った projects 配下の background-agent を接続方式の参考とする。契約枠を使う API 通信と API 従量課金を区別し、専用会話アプリと費用制約の判断は [ADR 0003](../adr/0003-dedicated-chat-with-chatgpt-plan.md) に記録する。
- scene-craft で対象作品を指定して行った会話を、原文と要約の両方で残す。別のチャットや外部メモは、人間が取り込みを指定したものを対象にする。
- 一作品に工程や検討テーマごとの複数の会話を持てるようにする。制作意図・採用済みの結果・制作履歴は作品単位で共有する。
- 契約枠の利用上限に達した場合は依頼と途中状態を保存して停止し、人間が再開する。通常の自動再実行を繰り返さず、追加課金の経路にも切り替えない。履歴の閲覧や手作業の記録は LLM を使わず続けられるようにする。
- 初期の対応環境は現在の PC と導入済みの版とする。読み取り専用の環境調査で Windows 11、Windows 側の Blender 5.2 と Photoshop 2026／27.10 の実行ファイル、および現在のシェルが WSL2 上であることを確認した。アプリの起動・ライセンス・自動操作の動作可否は未確認。別 OS や複数バージョンへの対応は将来範囲とし、Windows と WSL の役割分担は操作経路の調査後に決める。

<a id="production"></a>

## 工程別の制作支援

- 参考調査の成果物は、出典・参考にする要素・制作意図との関係をセットで残す。人間が採用した参考資料を次の工程へ渡す。
- シーン計画では物体の分解、位置関係、おおよその寸法、制作順序まで提案する。参考資料から判断できない構造は仮説として示し、人間が採用してから制作へ進める。
- モデリングは仮形状と、柱・屋根・ベンチなどの定型的な形状作成を初期対象とする。人間が部品ごとに編集できる状態で渡し、作品固有の細かな造形は人間が仕上げる。
- アセット検索は手元の素材ライブラリと外部の素材サービスの両方を対象にする。候補にプレビュー・出典・利用条件を添え、人間が選んだ素材を取り込む。外部サービスの具体的な選定は未確定。
- 植物・小物配置では、使う素材・配置する範囲・除外する範囲・密度・大きさのばらつきを指定できる。未指定の値はエージェントが案を出し、人間が後から個別調整できる状態で渡す。
- UV・画像テクスチャ適用では、人間が選んだ画像に対して UV 展開、木目などの方向・縮尺、材質への接続までを初期対象とする。既存の UV や材質を変更する範囲は実行前に明確にする。
- 空・海・照明・雲は、数値指定だけでなく「夕方の暖かい光」「穏やかな海」などの表現から設定案を作れるようにする。時間帯・天気・雲量・海面の様子などを会話で指定し、編集可能な 3D の設定として渡す。見た目の採否は人間が判断する。
- レンダー出力は、合成済み画像に加えて、人間が指定した要素を分けた複数ファイルの出力も初期対象とする。分け方は作品ごとに選ぶ。Photoshop への読み込み、レイヤー整理、レタッチ、再レンダーの反映など、その後の操作はすべて人間が行い、作業記録は scene-craft に残せるようにする。

<a id="works"></a>

## 作品・既存データの取り込み・派生

一作品は完成した背景イラスト1枚を目指す単位とする。検討中の構図・色違いは同じ作品に含め、昼と夜など別の完成イラストを目指す場合は別作品として扱う。

- 新規作品に加え、制作途中の `.blend`・`.psd` を取り込んで利用を開始できる。取り込み以前の制作過程は不明として扱い、過去の理由は必要に応じて人間が補足できる。`.psd` の取り込みは作業記録として扱い、Photoshop の自動操作を含めない。
- 初期から、既存作品の保存状態を起点に派生作品を作れるようにする。元作品と起点の保存状態を記録し、派生先の制作データや参照素材の編集が元作品に影響しないように扱う。

<a id="edits"></a>

## 編集案・採否・変更範囲・保護指定

- エージェントが変更できる範囲は、人間が触った箇所かどうかではなく、依頼で合意した変更範囲を基準とする。範囲内で編集案を作り、範囲外の変更が必要なら確認する。保護指定は対象全体と項目単位の両方に対応し、初期は位置・回転・大きさ・形状・材質・主要なカメラ／照明設定を対象とする。新しい依頼が既存の保護指定と競合した場合、自動で解除せず確認し、人間が変更を明示的に認めた場合に変更する。「今回は変更してよい」という許可はその依頼だけに適用し、次の依頼では保護を維持する。継続的な解除は別途明示する。
- 編集案は独立して判断できる変更ごとに採用する。例えば植物配置と照明調整は分け、一方が他方に依存する場合はまとめて確認する。
- 編集案を確認中に人間が直接手を加え、「修正して採用」できる。AI が作った状態と人間が直した状態を区別して残す。
- 初期は、エージェントが編集案を作っている間、同じ制作データを人間が同時編集しない運用とする。別作品の制作や参考調査は進められる。完成した編集案への手修正とは区別する。

<a id="records"></a>

## 制作履歴・手修正・Photoshop 作業の記録

- 手修正は意味のあるまとまりごとに変更前後と理由を結び付ける。Blender・Photoshop の両方で、人間が「ここまでを一つの修正として記録」と区切りを指定し、前回の記録からの変更をまとめる。理由は短い自由文で入力するか、未入力のまま後から補える。理由をその場で入力できなくても制作は続けられる。既存作品は取り込み時点を最初の記録にする。変更の検出方法は未確定。
- 初期の手修正の記録は、変更前後の制作ファイル・プレビュー・変更の要約・人間が入力した理由を基本とする。変更の要約は人間が訂正できる形にし、すべてのオブジェクトや内部設定の差分を網羅することは求めない。
- Photoshop 作業は人間が PSD とプレビュー画像を保存・書き出しし、それらと作業内容・任意の理由を scene-craft の作品に登録する。基盤側で前回の記録や元のレンダーに結び付ける。Photoshop 内部の保存・書き出しの自動操作は行わない。
- エージェント改訂履歴は、各実行と当時の指示・モデル・ツール・手順などの設定、および変更理由を結び付けて追跡できる範囲を初期対象とする。過去の実行環境の完全な復元は含めない。

<a id="execution"></a>

## 実行・停止・自動再実行

- 複数の会話から同じ制作データに編集を依頼した場合も、編集は順番に実行する。待機中の依頼は実行直前に最新の状態を参照し、先行する変更によって依頼の前提や変更範囲が合わなくなった場合は人間に確認する。
- ブラウザを閉じても、ローカルの実行プロセスが動いている間はエージェントやレンダーの処理を継続する。画面を開き直して進捗・結果を確認できるようにし、PC や実行プロセスが終了した場合は中断として記録して人間の指示で再開する。
- 初期から画面での途中停止に対応する。停止要求後は新しい操作を開始せず、実行中の操作は停止可能なところで止める。途中状態を記録し、人間による停止には自動再実行をかけない。
- 失敗時のエージェントによる自動再実行を初期から対象とする。接続の復旧や、同じ制作結果を目指した操作方法の修正は自動で進められる。素材の差し替え、形状の簡略化、配置・照明の変更など、デザインが変わるような再実行は人間に確認し、デザインを維持できるか判断できない場合も確認する。
- 自動再実行は一つの依頼につき最大2回、初回を含めて最大3回とする。途中でエラーの種類が変わっても回数をリセットせず、上限に達したら原因・途中状態・対応案を示す。
- デザインを維持する範囲で、その場で生成した操作スクリプトの自動修正を許可する。Git 管理しているツール・エージェントの定義自体を改訂する場合は、人間による確認とコミットの手順を適用する。

<a id="storage"></a>

## 保存状態・復元・削除・バックアップ・移行

- 初期のやり直しは、記録した時点の制作データへ戻る形とし、戻す前の状態も残す。後続の手修正を維持しながら以前の AI 編集だけを選択的に取り消すことは、初期対象に含めない。
- 過去の保存状態を復元するために必要なテクスチャやリンク素材も保存対象とする。保存できない外部依存がある場合は不足を示し、その保存状態を完全に復元可能とは扱わない。
- バックアップ・移行のために、人間の指示で制作ファイル・依存素材・会話・制作履歴・参照した Git コミットを保持するためのデータをまとめて書き出し、復元できる機能を初期から用意する。保存できたものと不足を示す。LLM を呼ばず通常のプログラムで実行し、契約枠を使えない場合も利用できるようにする。
- 不採用や失敗も含め、会話・採否・理由・失敗内容は記録に残す。大容量の生成物は人間が明示的に削除でき、削除後も記録は残して実体がなく復元できないことを示す。

<a id="style"></a>

## 振り返り・作風・制作方針

作風の傾向は人間が確認する仮説であり、人間が採用した制作方針と区別する。個々の作品の制作意図は、過去の作風の傾向や一般的な制作方針に優先する。

- 振り返りは、完成した一作品と複数作品を横断した分析の両方を初期対象とする。人間が対象作品を選んで起動し、具体的な作品・採否・手修正を根拠として示す。理由が未入力の箇所は意図を断定せず、仮説として扱う。
- 作風もバージョン管理の対象とする。「作風の傾向」と、人間が採用した「制作方針」の区別を維持して扱う。作品で使う作風の版は固定し、人間が選んだときに更新する。

<a id="versioning"></a>

## Git による版管理と更新運用

- バージョン管理は Git を正とし、ローカルのデータに独立した版番号を設けない。初期はツール・エージェントの定義と作風の傾向・制作方針を同じリポジトリで管理し、実行にはコミット済みの内容を使う。ローカルの記録にはフルコミットハッシュを保存し、タグは任意の表示名とする。エージェント定義と作風の参照するコミットが異なる場合も、それぞれ Git のハッシュで記録する。
- 制作ファイル本体は初期はローカルに保存し、各記録に使用した定義・作風の Git コミットを残す。作品・実行・保存状態を区別する ID は持つが、独立した版番号としては扱わない。版の判断の理由と未確定の境界は [ADR 0001](../adr/0001-git-authoritative-versioning.md) に記録する。
- 定義や作風の変更内容を人間が採用した後、エージェントが対象の変更をローカルにコミットする。そのコミットを以後の実行で参照し、リモートへの公開は別の操作として扱う。
- 通常の制作に使う変更を main に集約し、ツール・エージェントの追加や修正は feature/*・fix/*、作風の更新は style/* の短命なブランチで進める。変更ブランチのコミットを明示した試行も可能とし、制作データのコピーを使ってコミットと結果を記録する。
- 初期はローカルで人間が変更内容を確認して統合でき、PR は任意とする。初期構築完了後にツールや指示を更新するときに限り、検証は一律の必須条件にせず、コミットとマージの前にそれぞれ毎回、実施するか人間に確認する。省略を選んだ場合も進められ、実施有無と実施した場合の結果を記録する。それ以外では検証有無の確認は不要とし、変更に応じた適切な検証を行う。main にあることだけでは検証済みと扱わない。
- 元のコミットを保持するマージを使い、制作履歴から参照済みの履歴は rebase や squash で置き換えない。不採用の実験も、ブランチ削除前に保持用の Git 参照を残す。理由と運用の詳細は [ADR 0002](../adr/0002-short-lived-branches-and-human-validation-choice.md) に記録する。

<a id="acceptance"></a>

## 初期版全体の受け入れ条件

- 初期版全体の受け入れ条件には、実作品を通した確認を含める。一作品で各工程を個別に呼び出して 3D 制作からレンダーファイルの出力まで進められること、その後に人間が行ったレタッチも含めて編集案の採否・手修正・理由を記録して保存状態へ戻せること、一作品の振り返りと複数作品を横断した作風の言語化ができること、次の制作で採用した制作方針を指定した Git の版から参照できることを確認する。Photoshop 操作は人間が行う。これは毎回のコミット・マージで検証を強制する判断ではない。

<a id="boundaries"></a>

## 将来範囲と未確定事項

工程の自動進行、画面レビュー、Photoshop の自動操作、過去の AI 編集だけを選択的に取り消す機能、過去の実行環境の完全復元、別 OS・複数バージョン対応は初期対象に含めない。構図・カメラの最終判断は人間が行い、必要に応じて指定条件に基づく操作や比較案を支援する。雲を 3D で作るかレタッチで描くかは作品ごとに選ぶ。

LLM 接続の成立と費用条件、Windows / WSL の役割、Blender 操作経路、保存形式、実行状態、編集案と保護の実現方法、Git 参照の保持方法、具体的な素材サービスなどは、[設計項目一覧](../design/README.md) の Issue で決定する。背景となる検証実装の確認済み範囲と限界は [ADR 0003](../adr/0003-dedicated-chat-with-chatgpt-plan.md) を参照する。
