# バージョン管理の正を Git に統一する

2026-10-05 の要件インタビューで、ツールやエージェントの定義を Git で管理することを前提に、バージョン管理の正を Git に統一すると決定した。ローカルのデータには Git に紐付いた値をバージョンとして記録し、独立した版番号は設けない。別々のバージョン体系を維持し、その対応を管理する負担を避けるためである。

作風もバージョン管理の対象に含め、「作風の傾向」と人間が採用した「制作方針」の区別を維持する。初期はツール・エージェントの定義と作風の傾向・制作方針を同じリポジトリで管理する。

## 版の識別と適用

- 正式な版の識別子にはフルコミットハッシュを使う。タグは任意の表示名として併用できるが、ローカルの記録には参照先のコミットハッシュを保存する。
- 実行に使う定義・作風はコミット済みの内容に限定する。実際に使う内容と記録するコミットの内容を一致させる必要があり、未コミットの変更を使って現在のコミットだけを記録する運用は採らない。
- 定義や作風の変更内容を人間が採用した後、エージェントが対象の変更をローカルにコミットし、そのコミットを以後の実行で参照する。リモートへの公開は別の操作として扱う。
- 作品で使う作風の版は固定し、人間が選んだときに更新する。エージェント定義と作風で参照するコミットが異なる場合も、それぞれ同じ Git のコミットハッシュ体系で記録する。
- `.blend`・`.psd` などの制作ファイル本体は初期はローカルに保存する。各記録に使用した定義・作風の Git コミットを残し、制作ファイルの保存状態自体を Git の版として管理することは求めない。
- 同じ定義の版で複数回制作できるため、作品・実行・保存状態を区別する ID は持つ。これらは対象を識別するためのもので、独立した版番号としては扱わない。
- ブランチ運用、試行中のコミットの利用、参照済みコミットの保持方針は [ADR 0002](0002-short-lived-branches-and-human-validation-choice.md) に従う。初期構築完了後にツールや指示を更新するときに限り、検証の実施はコミット・マージの前にそれぞれ毎回人間に確認し、一律の必須条件にはしない。それ以外では検証有無の確認は不要とし、変更に応じた適切な検証を行う。

## 未確定の境界

- 実行記録から参照するコミットを保持する Git 参照の具体的な形式と保存・同期方法。
- ローカルの保存状態と依存素材を保存する具体的な方法。依存素材も保存対象とし、保存できない外部依存がある場合は不足を示す方針は決定済み。

この判断は、外部ツールの提供元が定める製品バージョンを Git の識別子に置き換えることや、過去の実行環境の完全な復元を決めるものではない。
