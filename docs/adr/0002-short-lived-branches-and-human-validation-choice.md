# 短命の変更ブランチを使い、検証の実施は毎回人間が選ぶ

2026-10-05 の要件インタビューで、通常の制作に使う変更を main に集約し、ツール・エージェントの追加や修正は feature/*・fix/*、作風の傾向や制作方針の更新は style/* の短命なブランチで進めると決定した。作品の使用版はブランチ名ではなく [ADR 0001](0001-git-authoritative-versioning.md) の Git コミットで固定する。作風の更新を main に統合しても、進行中の作品へは自動適用しない。

## コミットと統合

変更内容の採否は人間が確認する。初期はローカルでの確認・統合を可能とし、GitHub の PR は任意とする。

検証はコミット・main へのマージの一律の必須条件にしない。コミットの前、マージの前に、それぞれ毎回、検証を実施するか人間に確認する。変更が小さいというエージェントの判断で確認を省略したり、前回の回答を引き継いだりしない。人間が検証の省略を選んだ場合もコミット・マージを進められる。検証の実施有無と、実施した場合の結果を記録し、main に入っていることだけをもって検証済みとは扱わない。

これは、検証を常に強制すると小さな修正をすぐにコミット・マージしたい場面の負担になるためである。検証を一律に不要とする判断でもない。

## 変更ブランチでの試行

main への統合前でも、変更ブランチのコミットを明示して試せる。試行には制作データのコピーを使い、使用したコミットと結果を記録する。試すためのコミットと、通常の制作に使うための main への統合を区別する。

## 参照済みの履歴の保持

統合には元のコミットを保持するマージを使い、制作履歴から参照済みの履歴は rebase や squash で置き換えない。不採用の実験も、ブランチを削除する前に保持用の Git 参照を残す。ローカルの制作履歴にハッシュを記録するだけでは、参照先の Git オブジェクトが将来も保持されるとは限らないためである。

保持用の参照の形式と保存・同期方法は実装設計で決める。これは Git とは別の版番号を導入するものではない。
