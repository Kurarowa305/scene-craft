# 編集案の採用と保護指定

[設計 Issue](https://github.com/Kurarowa305/scene-craft/issues/8)。2026-10-18、利用者が3ラウンドのQ1〜Q10ですべて推奨案を承認した。同日、利用者が本書全体を最終承認し、設計を確定した。本実装・実機検証の完了を意味しない。

## 責務と前提

制作管理が、編集案の基準・変更範囲・保護指定・依存関係・採否・組合せを管理する。実行管理は作品単位の順序・停止・再実行予算、保存モジュールは固定実体・依存素材・保存の確定を担当する。

根拠は[初期要件](../requirements/initial-scope.md#edits)、[データモデル](domain-data-model.md)、[実行状態](execution-lifecycle.md)、[保存設計](artifact-storage.md)、[Blender連携](blender-integration.md)、[用語集](../../GLOSSARY.md)。既存の論理ID・保存・実行契約を用い、本書で別の実行状態や版番号を作らない。

AIは保存済み入力の作業用コピーを編集し、元ファイル・確定した保存状態を上書きしない。候補の生成・修正・確認だけでは作品の現在状態を切り替えない。同じ作品の編集・採用・組合せ・復元は直列に扱う。AI編集中は同じ制作データを人間が同時編集しない。GUIの未保存内容を自動取得できるとは扱わない。

## 編集案の作成と採否

1. 依頼について、目的、対象、変更してよい項目、独立した変更の単位、保護指定・依頼限定許可を明確にする。曖昧な指定は具体的な対象・項目を示して確認する。
2. 現在状態を起点にする依頼は実行直前に最新状態を固定する。候補への修正は明示した保存状態を固定し、最新の採用状態に差し替えない。
3. 入力の可用性、対象の同一性、変更範囲・最新の保護指定と許可、同時編集の有無を確認する。前提が変わって依頼や確認回答が合わなければ確認待ちにする。
4. 作業用コピーで変更し、変更範囲と保護の検査、ファイル・依存素材の保存検証を行う。検査済みの編集案だけを採用可能として提示する。
5. 人間は、特定の編集案・保存状態・範囲について採用／修正して採用／不採用を判断する。理由は任意で、未入力をAIの推測で補わない。代替案で選ばれなかった案は未選択として残し、自動で不採用にしない。
6. 適用前に、現在状態と判断対象、最新の保護指定・許可を再照合する。組合せが必要なら次節に従う。結果を固定・検証し、採否の適用結果と現在状態の更新を保存契約に従って確定する。

同じ基準からの案全体をそのまま採用でき、内容の変更がなければ、既存の確定した保存状態を現在状態にできる。採用だけを理由に同じ内容の保存状態を増やさない。

## 部分採用と組合せ

### 独立した変更と依存する変更

植物配置と照明調整など、単独で結果を確認・検証でき、他方なしで成立する変更は、作成時から別々に採否を判断できる単位にする。一つの依頼から複数の編集案を作ってよい。同じ目的の代替案は同じ基準状態から分岐し、一回の選択では一つを選ぶ。

共有材質・生成設定・配置条件等を通じて一方が他方を必要とする場合は、その依存を明示して一組で確認する。見かけの分類名が違うだけで独立と判定しない。完成後に任意の細部だけを取り出したい場合は、元の案を上書きせず追加の修正案を作る。任意の内部差分を自動抽出・適用できることを初期の保証にしない。

### 基準が古い案、複数の案の組合せ

案の基準と現在状態が違う場合、古い案全体で現在状態を置き換えない。現在状態を起点に選択した変更を取り込む結果を別に準備し、人間が確認してから採用する。独立した複数の案を組み合わせる場合も、実際の組合せ結果を確認対象にする。

取り込み前に、変更対象と参照先、共有データ、保護、対象の存在・同一性を比較する。対象の削除・置換、同じ項目の変更、依存する設定の変更等があれば競合として扱う。配置や材質等のデザイン変更、残す手修正の判断が必要なら作業前に確認し、無断で変更・省略しない。

組合せをプログラムで正確に構成できる場合も、現在状態への適用前に結果を確認する。AIによる修正が必要なら新しい制作依頼・編集案として記録する。単なる通知再送や照合と、制作操作のやり直しは[実行状態設計](execution-lifecycle.md)に従って区別する。

組合せの変更前は、その時点の現在状態とする。取り込んだ編集案・採否・保存状態・採用範囲は寄与元として残し、直前の状態と混同しない。元の案は保持する。結果の確認後に現在状態等が再度変わった場合は再照合し、異なる内容への確認を流用しない。

## 候補の修正と採用の切替

未採用の案に手修正を登録し、その状態を指定してAIへ追加修正を依頼できる。手修正とAI修正を交互に続けても、採用前は現在状態を維持する。AI修正は新しい依頼・編集案・保存状態を作り、修正元の案と起点へ結び付ける。手修正は変更記録として、その対象案と前後の状態を保持する。

各段階の指示者と変更者、指示原文、理由、保存状態を区別する。最後に確認した具体的な案・状態を「修正して採用」の対象にし、未確認の枝先へ採否を移さない。Photoshopの編集は人間が行い、保存したPSD/PSBとプレビューを登録する。

採用済み案Aから別案Bへ切り替えたい場合は、現在状態を起点にBを取り込む修正案を作る。A採用後の手修正と競合すれば、残す部分・置き換える部分を確認する。過去のAI変更だけを選択的に取り消す保証はしない。過去状態へ丸ごと戻したい場合は、直前の状態を残す[復元手順](artifact-storage.md#過去の保存状態へ戻す)を使う。過去の採用判断・理由は上書きしない。

## 保護指定の対象と項目

保護指定は作品で共有する。対象全体と項目単位の両方を扱い、対象の表示名だけで識別しない。指定時に具体的な項目と対応範囲を示す。

| 項目 | 保護する内容 |
| --- | --- |
| 位置・回転・大きさ | 対象の変換と、その結果に影響する親子関係・制約等。カメラでは実際の撮影位置・向きも含む |
| 形状 | メッシュ、形状を変えるモディファイア、生成設定等 |
| 材質 | 材質の割当、ノード、参照画像、UV等の対応する設定 |
| 主要なカメラ設定 | レンズ、投影方式、シフト、被写界深度、使用カメラの切替。カメラ全体の保護では位置・向き等も含む |
| 主要な照明設定 | 位置・向き、種類、色、強さ、大きさ。環境光は別の保護対象として指定する |
| 対象全体 | 上記の該当する項目に加え、削除、置換、表示／レンダーの有効無効 |

共有データ・親子関係・制約等を介した間接変更も検査する。名前変更でも同一性を追跡できる識別子を用い、削除・再作成によって保護を回避しない。識別子が欠落・重複する、参照先を同定できない等の場合は、勝手に別対象へ保護を移さず、対応付けを確認する。識別子の具体的な埋め込み・継承方法は実装仕様で検証する。

共有材質等を編集すると保護対象にも変更が伝わる場合、必要に応じて編集対象側を分離し、保護対象を維持する。分離によって見た目や構造が変わる場合、または維持を検証できない場合は事前に確認する。保護解除や許可の確認と、検査方法・対応範囲の解決は別であり、許可だけで検証不能の結果を採用可能にしない。

カメラ保護は撮影位置・向き・設定等を維持する契約とし、画像全体の見た目を固定する意味にはしない。植物の追加による遮蔽等は依頼の変更範囲に沿って判断する。「この部分を隠さない」等の条件があれば別途明示し、検証方法を含めて合意する。

## 依頼限定許可・継続的な解除・手修正

保護と依頼が競合した場合は、自動解除せず、必要な対象・項目・変更と理由を示して確認する。依頼限定許可は依頼ID・対象・項目・許可範囲・指示原文・判断者・時刻に結び付ける。「位置だけ」の許可をレンズや材質の変更許可へ広げない。継続的な解除は別の明示的な判断として記録する。

同じ依頼の再実行には許可を引き継ぐが、目的・対象・範囲や最新の保護と整合していることを確認する。新しい追加修正依頼へは引き継がない。許可を使って変更した候補を起点にすることはできるが、そこから同じ保護項目をさらに変更するには新しい許可が必要となる。

許可済みの案を採用する際は、その案を作った依頼・許可と実際の変更を照合し、無関係な依頼の許可を流用しない。生成後に保護が変更された場合や、組合せで許可範囲を超える変更が必要な場合は再確認する。

人間がBlenderで保護項目を変更した場合も手修正として登録でき、保護指定は維持する。その手修正済み状態を起点にするAIは、そこから保護項目を変更できない。人間の手修正をAIへの継続的な解除や依頼限定許可と解釈しない。登録の由来は手修正とし、AIの範囲外変更を手修正に読み替えない。

## 実行前後の検査

実行前に対象・項目・許可を解決し、許された操作に制限する。実行後は入力と出力について実際の変更を検査し、変更範囲外や保護対象への直接・間接変更がないことを確認する。操作スクリプトの予定やAIの自己申告だけで合格させない。

検査は、対象ID・設定・参照先・共有関係等、対応する比較情報を保存状態に結び付け、検査対象・方法・結果・検証不能な項目を記録する。生成スクリプトも同じ制約と検査を通す。制作ファイル外の素材を変更して検査を回避させず、管理下の固定素材を直接変更しない。

| 結果 | 扱い |
| --- | --- |
| 範囲内・保護維持を検証できた | 保存・依存関係等の検証も通ったものを採用可能な案として提示 |
| 範囲外変更・保護違反 | 違反内容を示し、結果は採用可能として提示しない。確認用記録を保持し、現在状態を維持 |
| 対応外設定・比較不能・対象同定不能 | 不明な項目を明示し、検証済みとしない。必要な確認・対応可能な方法を提示 |

違反や検証不能の結果を、人間の採用クリックだけで検査済みにしない。範囲・許可の見直し等が必要なら合意し、検証できる方法で作り直す。再実行で済む技術的な失敗は同じ依頼の累積回数を使い、目的・範囲を変える制作指示とは区別する。回数をリセットするための新規依頼にしない。

## 採用失敗と結果不明

採用指示は採否記録として保持し、適用結果を未適用／適用済み／失敗／不明で区別する。制作ファイルと依存の検証、固定実体の確定とDBの照合が成功するまで現在状態を切り替えない。現在状態の更新と更新記録はDB内で一体として確定する。

失敗時は直前の現在状態と案を維持する。結果不明なら操作ID・入力・結果ハッシュ・完成記録・DBを照合し、同じ採用を二重実行しない。照合できるまで競合する変更を開始しない。

確認済みの同じ結果を確定するだけなら採用の再確認は不要とする。ただし、入力・現在状態・保護・許可等の前提を再検査する。内容や前提が変わる場合は確認を取り直す。再開や再実行の許可は[実行状態設計](execution-lifecycle.md)に従い、この規定で停止後の自動再開を許可しない。

## 具体例と受け入れ観点

以下は設計上の確認シナリオであり、実装で確認済みという意味ではない。

| 状況 | 期待する流れ |
| --- | --- |
| 植物だけ採用、照明は不採用 | 基準Sから植物Pと照明Lを独立して作り、Pを採用、Lを明示的に不採用。Pの検証済み状態を現在状態にし、Lの変更を混ぜない |
| 植物と照明が依存 | 依存理由を示して一組で確認。植物だけにしたい場合は独立して成立する修正案を追加で作る |
| 修正して採用 | 未採用P→手修正H→AI修正P2。各状態と修正元・指示・変更者を残し、確認したP2の状態を採用。それまでは現在状態を維持 |
| 確認中に別案を採用 | S基準の植物Pを確認中に照明Lを採用。Lを起点にPを取り込む結果Mを別に作り、Mの確認後に切り替える。L・Pを寄与元として記録 |
| カメラ保護との競合 | 植物配置に伴い親オブジェクト経由でカメラが動くなら禁止。必要な変更を事前確認し、今回の位置変更だけを許可。次の追加依頼には許可を引き継がない |
| 共有材質と保護 | ベンチと小物が同じ材質を共有。ベンチ保護を維持するため小物側を分離。見た目・構造の変化が必要、または維持を検証できないなら事前確認 |
| 保護対象への手修正 | 人間がカメラを移動して手修正登録。保護は維持し、その状態を起点とするAIはさらに移動できない |
| 採用後の別案への切替 | A採用後の手修正Hを起点にBを取り込む修正案を作る。Hと競合する部分の扱いを確認。丸ごとの巻戻しは履歴を残す復元を使用 |
| 範囲外変更・検証不能 | 違反・不明な項目を示し、採用不可。記録と元の状態を保持し、合意・検証可能な方法に基づいて作り直す |
| 採用中の保存失敗・通知喪失 | 指示を残して現在状態を進めず照合。既に確定した同じ操作なら重複登録しない。内容変更が必要なら再確認 |

対象IDの具体的な実装、Blenderの対応プロパティ一覧、項目ごとの比較方法・数値比較条件、共有データの分離、組合せ操作の実現性は実装仕様と検証で具体化する。対応不能な項目を黙って検査対象から外さず、制約と必要な確認を明示する。本書は任意のBlender設定・任意の差分の自動マージを保証しない。
