# LLM 接続と費用制約

2026-10-12、[LLM 接続と費用制約を満たす方式を決める](https://github.com/Kurarowa305/scene-craft/issues/2) の設計を利用者と合意した。Codex app-server と Codex 管理の ChatGPT 認証を採用する。費用条件の確認は利用者が担い、基盤側の確認と利用枠・残高の取得失敗による送信保留は設けない。モデル選択、依頼の最大2回の自動再実行、停止・手動再開、実装時の異常系検証方針を以下にまとめる。接続の主要な実機確認は完了しているが、本実装の完了を意味しない。

## 合意済みの構成と責務

- 初期からローカル Web アプリを用意し、Codex app-server をエージェント実行基盤として採用する。エージェントの実行処理と文脈管理の自作を減らすことを優先する。[ADR 0004](../adr/0004-codex-app-server-runtime.md)
- scene-craft は作品・保存状態・編集案の採否・保護指定・手修正と制作履歴を管理する。Codex の会話と作品の対応を保持し、圧縮後の文脈だけを制作履歴の原文として扱わない。
- 工程ごとに人間がエージェントを呼び出す初期範囲を維持する。app-server の採用だけを理由に工程の自動進行を導入しない。[初期要件](../requirements/initial-scope.md#scope)
- LLM 利用は ChatGPT Pro の契約内とする。自動補充無効・既存クレジットなしの確認は利用者が行う。scene-craft は費用確認の操作・記録・有効期限管理を持たず、利用枠・残高の取得失敗を理由に送信を保留しない。API 従量課金への切替は用意しない。専用 SIWC 案で合意したアプリ単位のクレジット利用無効設定が、Codex 管理の認証にも適用されるとは扱わない。[ADR 0003](../adr/0003-dedicated-chat-with-chatgpt-plan.md)
- 利用上限や人間の停止では途中状態を残して止まり、人間が再開する。LLM を使わない閲覧・手作業の記録・バックアップは継続できる。[初期要件](../requirements/initial-scope.md#execution)

## 認証方式（合意済み）

Codex 自身の ChatGPT ログインを採用し、ログイン・認証情報の保存・トークンの自動更新を Codex に任せる。scene-craft は専用 OAuth 登録や更新処理を持たず、接続状態と再認証が必要な状態を扱う。エージェント実行・文脈管理と同じく、自作と保守の範囲を減らすためである。[ADR 0004](../adr/0004-codex-app-server-runtime.md)

2026-10-06 に利用者が「自動補充は無効」「既存クレジットはない」と確認し、その条件で Codex 管理の認証に確定した。この二条件を費用面の運用前提とする。アプリによる自動検証や将来の設定変更を含めた課金防止の保証とは区別し、API 従量課金への切替も引き続き設けない。

比較した scene-craft 専用の Sign in with ChatGPT は、外部アプリ向けのクレジット設定と対応付けやすい一方、認証・保存・更新を自作する負担があるため採用しない。比較の根拠は [専用 OAuth を使う app-server 構成](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) と [Codex の認証方式](https://learn.chatgpt.com/docs/app-server#auth-endpoints) を参照する。

### Codex 管理の認証で分かった費用上の条件

詳細と一次資料は [認証と費用の調査](../research/codex-managed-auth-billing.md) に記録した。以下は当時の調査結果と制約であり、実装済みの制御ではない。調査資料に残る機械側の費用確認案は、2026-10-12 の合意により採用しない。

- API キーの課金経路は、ChatGPT 認証の強制、接続先の固定、API キーや別 provider 設定の混入防止で制限する。上限到達で自動的に API 課金へ移る仕様は確認されていない。
- ChatGPT 認証でも、契約枠を超えると既存クレジットを消費し得る。さらに自動補充が有効なら残高低下による追加購入が発生する。自動補充を無効にしても、既存残高の消費は防げない。
- 利用枠・残高の API は監視に使えるが、次の推論のクレジット不使用を強制するものではない。並行利用や実行中の枠消費があるため、開始前の残量確認だけを費用保証にしない。
- Codex 管理の認証に対するアプリ単位のクレジット不使用設定は、公式文書と導入済み CLI の schema では確認できていない。利用者による自動補充無効・既存クレジットなしの確認を採用判断の根拠とし、契約枠限定の条件は維持する。

## 接続と復旧の契約

以下は2026-10-12に合意した接続領域の契約。OS ごとの配置、制作操作の重複防止、ツール接続方式などの詳細は末尾の後続 Issue で具体化する。

| 項目 | 合意した契約 |
| --- | --- |
| アプリとの通信 | scene-craft のローカル実行プロセスから stdio で app-server を管理する。検証では Windows 側の SQLite 保存先で起動に失敗し、WSL 側へ分けると成功した。製品の保存先は OS の責務設計と合わせる。ブラウザを閉じても実行プロセスが動いていれば維持する |
| 会話 | scene-craft の会話と Codex thread ID を対応付け、依頼と turn ID、ツール要求と操作記録を結び付ける。要約・原文・制作状態を区別する |
| 成功判定 | 途中本文を表示しても、終端通知の成功状態を確認するまで完了扱いにしない |
| 認証情報 | 実行環境の専用保管先に保存し、ブラウザや制作データのバックアップへ含めない。具体的な保管方式は Codex の設定と Windows/WSL の責務設計に合わせる |
| 費用設定の確認（合意済み） | 利用者が行い、基盤側の確認・確認記録・送信条件にはしない。利用枠・残高の取得失敗でも送信を保留しない |
| トークン更新 | 保存・自動更新を Codex に任せる方針は合意済み。scene-craft が扱う再認証の状態と、更新前後の制作操作の重複防止・継続の条件を具体化する |
| 再認証（手動再開は合意済み） | 失効・権限不足・一時的な通信障害を区別する。一時障害だけで資格情報を削除しない。再認証が完了しても、中断した制作操作を無条件で再実行しない |
| 再試行（回数の扱いは合意済み） | Codex 内部の通信再試行と scene-craft の依頼再実行を区別して記録する。利用上限と人間の停止を除外し、依頼全体の最大2回を超えない制御を設計する |
| モデル（選択単位は合意済み） | 制作会話については、設定画面にアプリ共通のモデル既定値は設けず、直前のチャットで選択していたモデルを新規会話へ引き継ぎ、会話ごとに変更できる。使用可能なモデルから選び、実行に使ったモデルを記録する。選んだモデルが使えない場合は利用者に変更を求め、自動で別モデルへ切り替えない。初期の既定値は下記のモデル選択を参照 |
| ツール | ローカル MCP と動的ツールを比較し、許可された変更範囲・保護指定を制作操作の実行側でも確認する。具体的なツール契約は後続設計へ引き継ぐ |

公式の thread/turn 機能、動的ツールの実験扱い、比較した専用 OAuth 案の再起動条件は [比較調査](../research/llm-connection-options.md) を参照する。app-server に会話再開があることを、外部の制作操作の復旧保証とは扱わない。

## モデル選択

### 合意済みの選択単位

制作会話については、設定画面にアプリ共通のモデル既定値は設けず、直前のチャットで選択していたモデルを新規会話へ引き継ぐ。会話ごとに利用者がモデルを変更できる。実行に使ったモデルを記録し、選んだモデルが使えない場合は利用者へ変更を求める。別モデルへの自動切替は行わない。

### 初期値と変更の適用

2026-10-26、画面設計で利用者が「モデルの既定値」の設定を削除し、直前のチャットで指定していたモデルを引き継ぐよう指定した。以下は2026-10-12のアプリ共通既定値を設定する判断を更新したものとする。

- 過去にモデルの選択がない初回のみ、app-server が示す利用可能な既定モデルを初期選択として使う。独立したアプリ既定値の設定項目は持たない。具体的なモデル名は固定せず、既定モデルを取得できない場合は利用者が選ぶ。
- 新しい会話は直前のチャットで選択していたモデルを引き継いで保存する。作品作成や振り返り専用会話でも同じ扱いとし、既存会話の選択は自動変更しない。
- 会話のモデル変更は次の依頼から適用し、実行中の依頼や自動再実行の途中では切り替えない。停止した依頼を別モデルで再開する場合は利用者が明示して選び、同じ依頼の再実行回数は維持する。
- 初期の推論強度は選択モデルの既定値、速度は標準とする。モデル・推論強度・速度の実行設定を記録する。設定画面の詳細は画面設計で扱う。

以前の接続検証で使った `gpt-6.1-sol`・low・標準速度は当時の検証条件であり、特定モデル名や low を製品の初期値へ固定するものではない。

### 命名・保存用要約の補助モデル

2026-10-31、[エージェント契約の設計](agent-contracts.md#提案数と補助モデル合意済み)で、利用量・コストを抑えるため、命名・保存用要約には制作会話と別のモデルを使うと合意した。設定に「命名・保存用要約モデル」を設け、初期値はGPT-6 Luna（`gpt-6-luna`）、利用者が変更できるようにする。制作会話のモデル引き継ぎ・会話別選択は引き続き上記の契約に従う。

補助処理ごとに選択モデルと対象を固定・記録し、設定変更を実行途中へ遡って反映しない。指定モデルが使えなくても別モデル・provider・API課金へ自動切替せず、未命名・未要約として原文と制作結果を保存する。補助処理の失敗で記録保存を止めず、人間の停止後に新しい補助LLM処理を始めない。

## 費用確認と接続・復旧

### 費用条件の責務（2026-10-12 合意）

自動補充が無効で既存クレジットがないことは、利用者が確認・管理する。scene-craft 側には費用確認の画面、確認済み記録、アカウントとの照合、再確認や確認の無効化の仕組みを設けない。初回・再ログイン・設定変更時にも、基盤が利用者へ費用確認を要求する設計は採らない。

利用枠・残高の取得成功、`ordinaryUsageAllowed`、残高0などを送信前の必須条件にしない。これらの情報が取得できない場合も、それだけでは送信を保留しない。利用情報の表示を設ける場合も、取得できなければ不明として表示し、送信可否の条件とは分ける。

この判断は費用条件の確認を利用者へ委ね、基盤側の確認処理を不要にするためである。ChatGPT Pro の契約内で利用し、API 従量課金へ切り替えない要件は維持する。基盤が追加課金なしを自動保証する設計とは扱わない。過去の調査や検証で利用枠・残高を取得した事実は、製品での必須判定を意味しない。

### 送信と停止の境界

以下は既存要件を具体化し、利用者と合意した送信・停止条件。

- Codex 管理の ChatGPT 認証と採用した接続設定を使い、API キーや別 provider へ自動で切り替えない。認証が必要な場合は再認証を案内する。
- 停止要求、受付結果不明、前の実行の未解決状態を確認する。同じ制作データの実行順と変更範囲は制作操作側でも確認する。
- 利用情報の取得失敗と、実際の実行で契約枠の上限に達して停止したことを区別する。上限到達時は途中状態を保存し、人間が再開する既存要件を維持する。
- 費用確認記録や残高取得の成否による送信・再開の判定は設けない。

### 停止・復旧の判断

認証切れ、PC・実行プロセス終了後は、復旧しても制作を自動再開せず、人間の再開指示を待つ。実行済み操作を照合し、実行したか不明な操作を自動で繰り返さない。この方針は2026-10-12に合意済みで、下表はその具体化を含む。

| 状況 | scene-craft の扱い | 再開・再送 |
| --- | --- | --- |
| Codex 内部で復旧中（`error.willRetry=true`） | 進捗として表示し、同じ turn のイベントを受け続ける | scene-craft から重ねて依頼を送らない。契約枠上限・人間の停止条件は別途優先する |
| 正常終了 | `turn/completed.status=completed` を確認し、終端と結果を保存する | 途中本文の受信だけでは成功としない |
| 契約枠の利用上限到達 | 新しい依頼と制作操作を止め、途中状態を残す | 利用可能性が戻っても自動再実行せず、人間の再開を待つ |
| 認証が必要 | Codex の通常の更新で回復しなければ、再ログインが必要と表示する | 一時的な通信障害だけでログアウトや資格情報削除をしない。再ログイン・途中状態の照合後、人間が再開する |
| 確定した一時障害による失敗 | 最終失敗、実行済み操作、残りの再実行回数を確認する | 同じ制作結果を維持でき、重複実行を防げる場合だけ自動再実行する |
| `turn/start` の受付結果が不明 | ローカルの依頼記録、既知の turn/item、`thread/read` の履歴を照合する | 履歴に見つからないことだけで未実行と断定しない。対応を確定できなければ自動再送しない |
| 人間の停止 | 停止要求を保存し、新しい操作を止め、`turn/interrupt` を要求する | 自動再実行しない。停止完了前は「停止中」とし、終端不明なら「状態確認が必要」とする |
| PC・実行プロセスの終了 | 中断として記録し、再起動後に会話履歴と制作操作の記録を照合する | ローカルアプリを再起動しただけでは制作を再実行しない。人間が再開を指示する |
| 一般的な HTTP 429・原因不明のエラー | 契約枠上限と短時間のレート制限を混同せず、エラー種別と現在の利用枠を取り直す | 原因が不明なまま通常の自動再実行へ流さない |
| 保護指定・権限・設定・文脈上限などのエラー | 原因と必要な対処を表示し、関連する処理を止める | 権限を自動で広げたり、別モデルや別 provider へ逃がしたりしない |

`error` の受信と turn の終端は別である。`willRetry=false` だけでも成功・失敗の永続化完了を保証したとは扱わず、終端通知を待つ。通知を受け取れない切断では「状態確認が必要」とする。停止要求と完了通知が競合した場合も、実際に確認できた結果と停止要求を両方残し、完了済みの操作を取り消せたとは表示しない。

### 再実行回数と自作範囲

2026-10-12 に利用者と合意した。Codex 内部の HTTP/ストリーム再送は Codex に任せ、scene-craft が制作依頼をやり直す回数を一依頼あたり最大 2 回（初回を含め最大 3 回）とする。通信復旧のループは自作しない。Codex の二種類の retry 設定をそれぞれ 2 にしても、依頼全体で 2 回になるわけではない。

scene-craft は元の依頼 ID と累積の再実行回数を保持し、原因・turn・モデル・プロセスが変わっても回数をリセットしない。再実行は最終失敗後に、認証・停止状態、制作状態、同じ結果を維持できることを確認してから行う。デザインが変わる、判断できない、既に何が実行されたか分からない場合は、人間が判断する。

この上限は新しい turn の回数だけでは強制できない。モデルが同一 turn 内で制作操作を修正して再度呼ぶ場合も、制作操作側で同じ依頼の再実行予算を確認する必要がある。何を一回として数え、成功した操作と再実行をどう対応付けるかは、[実行状態・順序制御・再実行・復旧を決める](https://github.com/Kurarowa305/scene-craft/issues/7) と [工程別エージェントの入出力とツール契約を決める](https://github.com/Kurarowa305/scene-craft/issues/9) で具体化する。通信再送通知の件数をその回数の代わりには使わない。

scene-craft の接続処理が持つのは、実行前の条件確認、依頼と thread/turn の対応、進捗と終端の記録、停止要求である。OAuth 更新、モデルとツールの往復、文脈圧縮、内部通信の再送は Codex に任せる。認証情報の実体は Codex 標準の保管機構に置き、ブラウザや制作データのバックアップへ含めない。OS 資格情報ストアとファイル保管の具体的な選択・配置は、起動 OS と一緒に後続設計で決める。

background-agent の専用 OAuth・Responses 直接接続・エージェントの実行ループは製品へ持ち込まない。検証済みの入出力・画像・会話再開・ツール往復という確認観点を再利用する。今回の一時的な実接続クライアントも製品コードの完成とは扱わない。

### 未確認の異常系の検証方針

実アカウントの上限を使い切ったり、資格情報を失効させたりせず、実装時に接続処理の入口でイベントと取得応答を模擬する。実接続済みの正常系を繰り返すためのテストではなく、次の判断を確かめる。

| 模擬する状況 | 必ず確認する結果 |
| --- | --- |
| 自動更新通知、利用枠・残高の取得失敗 | 費用の再確認や再ログインを強要せず、利用情報の取得失敗だけで送信を保留しない |
| ログアウト・認証失効、実行時の契約枠上限到達 | 認証が必要な状態と上限到達を区別し、費用確認を要求しない。上限到達では停止して途中状態を残し、自動再実行しない |
| 再試行通知の後に成功／最終失敗 | 内部再試行中の重複送信がなく、終端を一度だけ扱う |
| 受付応答の喪失、遅れて来る通知、履歴との対応不明 | 受付不明の依頼を新しい依頼として自動再送しない |
| 停止と完了の競合、停止要求後のツール呼び出し | 停止後に新しい制作操作を開始せず、確定した結果を正しく残す |
| エラー種別・turn が変わる再実行、プロセス再起動 | 元の依頼の回数を保持し、上限後に自動で続行しない |

これらはまだ実施していない検証計画である。外部ツールが既に変更した制作データの整合性は、制作操作とその記録を使う別の検証が必要となる。技術上の根拠と限界は [実接続記録の復旧設計補足](../research/codex-app-server-connection-validation.md#recovery-notes) に記す。

## 検証済み範囲と app-server の実接続確認

background-agent の応答完了・画像入力・再起動後の会話再開・モデルからのツール呼び出しは、2026-10-06 に利用者が検証済みと確認した。直接接続方式の同じ確認を繰り返さない。今回選んだ app-server は実行基盤が変わるため、その差分を以下の観点で確認する。

| 確認すること | 今回の結果と残る範囲 |
| --- | --- |
| 認証と費用条件 | Codex 管理の ChatGPT 認証と、通常契約枠の利用許可・クレジット残高 0 を取得。自動補充無効は利用者確認済み。設定の将来変化を自動保証したとは扱わない |
| 応答完了 | 本文差分の受信と `turn/completed.status=completed` を確認 |
| 画像 | 既知の画像の色・形・順序が実モデルの回答と一致 |
| 会話再開 | app-server を終了・再起動し、thread ID から再開。過去の識別文字列とツール結果を参照できた |
| ツール往復 | 動的ツールをモデルが呼び、クライアントの結果を使って応答を完了。再起動後はツール定義も復元された。MCP との正式な方式選択は別途行う |
| 文脈管理 | 圧縮の完了通知と圧縮後の継続を確認。`thread/read` で初回応答の原文も取得できた。長期の制作履歴保持は別途設計する |
| 認証更新 | `account/read(refreshToken=true)` と、その後の会話継続が成功。失効・取消からの再認証は未検証 |
| 停止と障害 | ツール結果待ちで中断し、`interrupted` として検出。明示的な再開で中断したツールを繰り返さなかった。通信障害・強制終了・利用上限の模擬は未実施 |

導入済み Codex CLI 0.160.0、stdio、Codex 管理の認証で実モデルへの接続を確認した。構成、応答、証跡、起動時の保存先の制約は [実接続確認](../research/codex-app-server-connection-validation.md) に記録する。製品の実装完了や Blender 操作の整合性まで検証済みとは扱わない。利用上限を実際に使い切る試験は行わず、必要な異常系は模擬する。

## 後続への引き継ぎと完了の範囲

2026-10-31の[app-server機能別調査](../research/codex-app-server-ui-capabilities.md)は、導入版0.166.0-alpha.5.1のschemaと非推論RPCを追加確認した。未認証でもmodel/listが返り、一覧を利用権限の証明にできない。paginated履歴ではincludeTurns全件取得が非推奨で、turns/itemsのページングに対応する。要求モデルと実モデルの区別、サービス側model/reroutedと自動切替禁止の実現範囲は後続で検証する。既存の0.160.0による推論・再起動・圧縮・中断の検証を、現行版の再検証済みとは扱わない。

本領域の接続方式・認証・費用確認の責務・モデル選択・停止と復旧・再利用範囲は合意済み。主要な接続機能の実機確認と、未確認の異常系を実装時に模擬する方針を根拠として後続設計へ進める。以下はこの Issue を開いたままにする未合意点ではなく、それぞれの設計領域で具体化する境界である。

- [アプリ全体と Windows・WSL の責務を決める](https://github.com/Kurarowa305/scene-craft/issues/3): stdio で接続する app-server の起動場所、プロセス管理、認証情報と制作データの配置。検証で生じた SQLite 起動失敗と保存先分離の制約を確認する。
