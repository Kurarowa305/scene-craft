# 工程別エージェントの入出力と外部ツール契約

[設計Issue](https://github.com/Kurarowa305/scene-craft/issues/9)。2026-10-31、利用者と10役割の入出力・完了条件、専用MCP、工程切替、Git定義、生成Python、提案数、命名・要約を合意した。操作相談は独立した結果記録を不要とし、回答の提示で完了する。以下を現在採用する設計とする。設計完了は本実装・実機検証の完了を意味しない。

## 責務と基本方針

- 選択した工程の目的に必要な検索・参照は、別工程でも使う補助機能を含めて許可する。素材は人間が選び、制作データの変更は依頼で合意した範囲に限定する。別工程のエージェントは自動起動しない。
- メインチャットでエージェント「なし」を選んだ通常送信では、相談・採否・手作業の記録・補記を扱える。新しい制作操作は工程を選んで依頼する。
- 「記録として送信」は通常送信とは別経路で、LLMを使わず保存する。
- 各エージェントがどのBlender MCP等の外部ツールを使うかも、本Issueの設計資料に含める。

上記の「なし」の権限を、相談専用のサイドチャットへ適用しない。サイドチャットでは既存の[画面設計](user-interface.md)どおり、制作操作・採否・手作業の記録・メインへの依頼の受け渡しを禁止する。

- 既製MCP for Blenderは初期採用しない。scene-craft用の制作ツールからWindows補助プロセスとBlender Pythonを利用し、保存済み入力コピー・background実行を維持する。
- 10役割と外部処理の対応は次表の構成を採用する。共通ツールのInterfaceは後述し、実装時の呼出名・スキーマはこの契約に従って確定する。

| 役割 | 採用する外部処理・共通機能 |
| --- | --- |
| 参考調査 | Web検索・ページ取得・参考資料保存 |
| シーン計画 | 資料参照・保存済みシーンの情報取得 |
| 仮形状・定型モデリング | Blender Pythonによる形状作成 |
| アセット検索・取り込み | 指定フォルダー・Poly Haven・ambientCG検索、取得、Blender取り込み |
| 周辺整備・植物・小物配置 | 素材取得、Blender Python・Geometry Nodes |
| UV・画像テクスチャ適用 | 素材取得、BlenderのUV・材質操作 |
| 空・海・照明・3Dの雲の設定 | 素材取得、Blenderの環境・形状・ノード操作 |
| レンダー出力・引き渡し | Cycles、EXR処理、PSD／PSB生成 |

2026-10-31、方式の説明後に利用者がQ5の専用stdio MCP採用を承認した。WSL上の専用ローカルMCPをCodexが起動し、バックエンドの制作処理へ要求を渡す。[全体構成図とプロセス責務](application-architecture.md)にも反映した。

## 引き継ぐ前提

- 初期対象は[要件](../requirements/initial-scope.md#scope)の10役割。人間が工程を選択する。工程数と常駐プロセス数は一致させない。
- 制作操作は[Blender連携設計](blender-integration.md)の保存済み入力コピーとWindows Blenderのbackground実行を使う。元のファイルや、人間が開いたGUIの未保存データを直接編集しない。
- 制作意図・採用状態・保護指定・作風・根拠は[文脈設計](context-and-style.md)から取得し、実際に渡した参照を固定する。追加取得も記録する。
- 変更範囲・直接および間接変更の保護検査・採用可否は[編集案設計](edit-candidates.md)に従い、実行側で強制する。
- 停止・結果不明・二重実行防止・依頼全体の最大2回の再実行は[実行状態設計](execution-lifecycle.md)に従う。
- 定義・作風の固定コミットと使用blob、runtimeの実版は[Git版管理設計](git-versioning.md)に従う。実行時の生成スクリプトと恒久的な定義改訂を区別する。

## 制作ツールと生成Pythonの分担（合意済み）

素材取得・対応形式の取り込み、入力コピー、保存・検査・プレビュー、レンダーパス取得とPSD/PSB生成はGit固定の通常プログラムで実行する。毎回モデルに保存・停止・色変換等の基盤処理を書かせない。

2026-10-31、利用者がQ4の推奨案を採用した。形状・配置・UV・材質・環境の具体化は、固定した共通手順を優先し、共通手順で表せない依頼に生成Pythonを使う。生成スクリプトも依頼の変更範囲、保護検査、停止、再実行予算を通し、入力とコード実体・ハッシュ、使用runtime、出力と検査結果を結び付ける。生成コードをツール定義やGit管理の共通手順へ自動昇格させない。

任意シェル文字列やモデルが選んだ任意パスをWindows実行要求にしない。モデルには対象ID・操作内容等を渡すInterfaceを公開し、入力コピー・所有する実行プロセス・出力先・保存確定は通常プログラムが管理する。依頼・権限・起点の正本は実行側から解決し、モデルの申告で変更しない。

生成Pythonを受け付けることと、許可外のファイル・外部通信等へアクセスできない保証は別である。コードの文字列検査やBlender終了コードだけで制約成立とせず、実行環境の制限と実際の出力検査を含めて検証する。範囲外・保護違反・比較不能は既存契約どおり採用不可。制約を満たせない操作は対応済みとして公開せず、原因と対応可能な方法を示す。

## 接続方式（合意済み）

scene-craft専用のstdio MCPを初期採用する。app-serverの動的ツールは初期の必須依存にしない。これは既製MCP for Blenderを採用する判断ではない。MCPの入口から呼ぶ実処理は、合意済みの制作管理・実行管理・Windows補助プロセスである。

公式資料と導入版schemaの確認結果は[接続方式の比較](../research/agent-tool-transport-options.md)を参照する。採用の合意は専用制作ツールを実装・検証した結果ではない。

動的ツールはapp-serverの呼出にthread・turn・callの対応を持ち、scene-craft側で直接要求を扱いやすい一方、実験APIへの依存とthreadに保存された定義の継続を考慮する必要がある。MCPも公開するツールの制限だけで制作権限を保証しない。いずれも、接続と依頼の権限を受付側で照合し、モデル引数の作品ID・役割名の申告で権限を得られないようにする。

工程切替で指示やツール権限が漏れない方法、相談用接続で更新を拒否する方法、停止と結果不明時の照合は方式の選定と分けて検証する。MCPの設定項目や動的ツールの呼出IDが存在することだけで、これらを保証済みとしない。

## 提案数と補助モデル（合意済み）

2026-10-31、利用者がQ6の推奨案を採用した。依頼あたりの既定の提案数は1案。人間が比較を指定した場合や、前提・方向性を選ぶ必要がある場合に複数案を出す。一つの提案に含まれる独立した変更は既存契約どおり別々に採否を判断できる単位にし、提案数を1にすることと混同しない。

Q7では、利用者が利用量・コストを抑えるため、会話名・保存用要約には制作依頼とは別の安価なモデルを使い、設定で変更できるよう指定した。

- 設定にアプリ共通の「命名・保存用要約モデル」を設け、初期構築時の初期値をGPT-6 Luna（`gpt-6-luna`）とする。制作会話で選ぶモデルや、直前のチャットからの引き継ぎとは別に保存する。
- 補助処理を受け付ける時点の設定を固定し、モデル・対象原文範囲・起点依頼と実行結果を記録する。設定変更は以後の補助処理へ適用し、実行中・同じ処理の再実行途中で黙って変更しない。
- 必要な認証・利用上限・停止契約は既存のCodex管理認証に従う。API従量課金への切替や、設定したモデルから別モデルへの自動切替を設けない。
- 補助モデルが利用不可・認証待ち・利用上限・処理失敗なら、原文・制作結果を保持し、未命名／未要約として示す。必要に応じて利用者が設定を変更する。制作結果やLLM不要の記録の保存を補助処理の成功待ちにしない。
- 人間の停止後に新しい補助処理を起動しない。LLMなしの「記録として送信」を、裏で命名・要約するLLM送信の入口にしない。
- 補助処理には制作操作・採否・制作意図等を更新するツールを公開しない。専用処理として結果を保存し、制作会話の選択モデルや役割を変更しない。

モデルIDは[公式Models文書](https://learn.chatgpt.com/docs/models?surface=web)の `codex -m gpt-6-luna` と照合した（2026-10-31）。実アカウントでの利用可否と製品の命名・要約品質を本確認で検証済みとは扱わない。API料金の比較からChatGPT契約枠での消費を保証しない。

## 同じチャット内の工程切替

同じ会話のCodex threadを継続し、共通指示に「現在の依頼の役割・固定版・権限を正とし、過去工程の記述を履歴として扱う」と定める。送信ごとの依頼入力に、選択工程の固定指示・手順と必要文脈を渡す。工程切替のたびに共有MCP設定を書き換えたり、読み込み済みthreadへのresumeだけで上位指示が置換されたと仮定したりしない。

公開ツールがあること自体を実行許可にせず、専用MCPの信頼済み接続とバックエンドの依頼記録を照合する。現在の役割・対象・範囲・保護・世代を受付側で強制し、古い指示をモデルが使っても許可外操作を拒否する。同じthreadでは一つの進行中turnとし、前turn・ツール・外部操作の終端と遅延通知を照合してから次の依頼へ権限を渡す。

サイド相談と命名・要約は制作会話から分けたthread・権限で扱う。サイドでは参照用ツールだけを公開し、受付側でも更新を拒否する。命名・要約は補助モデルを使い、制作会話のモデルと指示を変更しない。

共通指示やMCP契約自体を変更する場合は、同じthread IDと履歴を保つ安全な終了・cold resumeを検証してから利用する。設定の更新が保証できないときは切替を成功扱いにせず、原因と対処を示す。工程切替と、共通指示そのものの版変更を区別する。

根拠と確認限界は[工程切替の調査](../research/agent-role-switch-options.md)を参照する。信頼済み接続とturnの対応、遅延した旧要求の失効、迂回経路の制限は実装・受け入れで検証する。

| --- | --- | --- |
| `get_execution_context` | 追加取得したい文脈の種別 | 受付側で結び付けた依頼・役割・対象作品・起点・定義と作風・保護・範囲・許可・再実行残数と参照。モデル指定の役割へ切替しない |
| `find_records` / `read_records` | 許可された作品内の検索条件、記録ID、ページ指定 | 原文・要約・画像等への参照、取得範囲と不足。実際に渡した内容を実行へ記録。原文を要約へ置き換えない |
| Codex組込Web検索 / `search_assets`（専用MCP） | 目的、検索語、検索元、素材条件、ページ指定 | Web候補または素材候補。出典・確認日・プレビュー・利用条件・品質と人間の選択を保存する。一覧取得だけで素材選択・取得・採用を確定しない |
| `read_reference_page`（専用MCP） | 参照URL、取得目的 | ページ本文・確認日・出典と取得範囲。必要な実体の保存条件を調べ、参考資料保存へ渡す |
| `fetch_selected_asset` | 人間が選んだ候補ID、形式・品質 | 選択の根拠、取得実体・依存と保存検査。指定フォルダーやサービスの取得先を保存側で解決し、任意パスを直接受け付けない |
| `inspect_scene` | 許可された保存状態ID、対象ID、取得項目 | Blender Pythonによる保存済みシーンの情報。入力を編集せず、参照を固定する |
| `create_edit_candidate` | 起点・対象ID、操作種別とパラメーター、生成Pythonを使う場合は受付で固定するコード本文または検証済みコード参照、変更理由 | 作業用コピーで操作・保存・依存と範囲検査を行った編集案ID・保存状態ID・プレビュー。採用は別操作 |
| `render_deliverables` | 保存状態、合意済みカメラ・フレーム・出力設定 | 全出力検査後のファイル参照と形式・制作データ。レンダーパス・色変換・PSD/PSB生成は共通処理 |
| `get_operation_status` | この依頼で受け付けた操作の参照 | 保存済みの進捗・完成・停止・照合結果。状態を読むだけで操作の再実行を開始しない |
| `record_human_decision` | 明示された人間の指示原文ID、対象・判断種別・任意理由 | 参考資料／計画／編集案／方針等への選択・採否と適用結果。AIの提案を人間の判断へ読み替えず、同じ明示指示に重ねた確認は要求しない |
| `update_work_context` | 明示された人間の指示原文ID、制作意図・保護指定・依頼限定許可等の対象と内容 | 指示に対応する共有情報の更新・訂正履歴。許可を別依頼へ広げず、AIの推測で解除・更新しない |
| `record_manual_work` / `amend_record` | 明示指示原文ID、対象・本文・選択ファイル・訂正元 | 意味のある手修正・理由・文章の追加記録。変更者を人間とAIで区別し、以前の内容を保持する |
| `save_reference_report` / `save_scene_plan` / `save_reflection` | 出典・部品構成・仮説等の構造化項目と人間向け本文、根拠参照 | 工程成果物の保存。モデルは採用を自動確定しない。振り返りは実参照と観察できなかった範囲を残す |

Codex組込Web検索はapp-serverのturn/itemへ対応付け、検索・参照結果を実行記録に残す。MCPの依頼コンテキスト引数を組込ツールが持つとは仮定しない。組込Web検索から制作ファイルや採否を更新する経路は作らず、参考資料・素材の確定は専用の保存・判断ツールへ渡す。

全履歴の振り返りでは、対象作品集合と開始時点を固定した全履歴の索引を対象にする。ページングの未取得・欠損・削除済み実体を記録し、実際の分析範囲を結果へ残す。全対象の索引と取得状況を持つことを、全画像・実体をモデルが観察済みという意味にしない。

### 専用MCPからバックエンドへの接続

MCPとバックエンドはWSL内のUnix domain socketによるローカルRPCを使う。ブラウザのHTTP入口とは別にし、所有ユーザーだけが使えるソケットと専用起動時の接続資格でMCPを識別する。接続資格は通常のモデル入力・ログ・Gitへ渡さない。stdioと内部RPCの要求・結果・切断はMCPアダプターが変換し、業務判断はバックエンドが行う。

モデルが保持する会話履歴だけで現在の権限を決めないため、バックエンドが各実行へ変更不能な依頼コンテキスト参照を発行する。モデルには今回の参照を渡し、すべての専用MCPツール呼出で提示させる。参照はバックエンドで接続・会話・依頼・AI実行・世代・現在turnへ照合し、自由入力の依頼IDや工程名では代替できない。サイド相談へは参照権限だけの参照を発行する。

これはモデルへ認証資格を預ける方式ではない。コンテキスト参照だけではバックエンドへ接続できず、別接続・別世代・終了済み実行へ流用できない。受付原文と操作内容への権限はさらに検査する。古いMCP要求が遅れて届いても、その古い参照を次turnの権限へ読み替えない。

MCPが複数の会話を扱う場合も、プロセスの「今の依頼」へ無条件に紐付けず、接続資格と各コンテキスト参照の対応を検査する。MCPプロセスの具体的な共有数は実装時に選べるが、この契約を緩めない。対応付けが不明・不一致なら実行しない。

### 信頼する受付情報と入力

モデルの引数とは別に、バックエンドが依頼ID、親のAI実行、受付原文、会話の種別、現在の役割、対象作品集合、実行世代・所有権を接続へ結び付ける。許可される操作と対象はこの情報と保存済みの合意から解決する。モデルが書いた依頼IDや役割名で別依頼・別作品の権限を得られるようにしない。

操作前に、起点、変更対象と項目、最新の保護・依頼限定許可、必要依存、前提の版を検査する。曖昧な対象・人間の判断が必要な事項は具体的な問いとして返し、その操作を始めない。停止・所有権不明・結果不明の競合があるときも新たな制作操作を始めない。

モデルへ返す共通結果は、依頼コンテキスト参照、永続操作ID、操作種別、入力参照、結果・進捗、成果物参照、検査結果、確認事項、失敗原因と再実行判定を持つ。既存の実行状態を使い、MCP専用の制作状態遷移を追加しない。長時間処理は受付済みの操作IDを返し、状態取得を継続する。ソケット・MCPの受付応答と実行の完成記録を区別する。

### 操作と結果の記録

- 実行管理がツール呼出と操作ID、実行ID、試行の対応を永続化する。入力の正規化内容・ハッシュ、起点、使用コード・定義版・runtime、開始と終端、出力参照・ハッシュ、検査方法・結果を結び付ける。
- 同じ操作IDで同じ内容を再送した場合は、受付済みの進捗・結果を返し、二重実行しない。同じIDで内容が異なれば拒否する。MCPの一時的なリクエストIDだけを永続操作IDにしない。
- ツール結果には、操作の参照、完了の有無、進捗、生成物・編集案・保存状態等の参照、検査結果、確認が必要な点、失敗原因を返す。MCPの成功は制作実体の完成・採用の成功とは区別する。
- 外部処理が続くときは操作参照を返し、後続の状態取得で照合できるようにする。タイムアウトだけで新しい操作IDを発行して再実行しない。待機・停止・終端は既存の実行管理を正とする。
- 失敗は、入力や依存不足、保護・範囲違反、未対応・検証不能、認証・利用上限、既知の一時障害、停止、結果不明等の原因を区別する。再実行の可否をモデルの自己判断に委ねず、実行管理が同じ依頼の累積予算と結果同一性・重複防止を検査する。
- 失敗した制作処理の修正・やり直しは同じturn内でも依頼全体の再実行回数を消費する。正常な別操作の続行、状態取得、同じ操作の通知・通信再送は制作のやり直しと区別する。

ツールの細分化や生成コードの変更で最大2回の予算を回避させない。LLMが新しいIDを指定したという理由だけで新規の制作目的として扱わない。受付原文・元の目的・失敗操作との対応は実行管理で保持する。

人間の停止は画面からバックエンドへ直接要求でき、モデルが停止ツールを呼ぶことを待たない。LLMなしの記録・プレビュー生成も同じ制作管理・保存・実行処理を直接使い、MCPやモデルの応答を前提にしない。

## Git管理する定義

役割ごとに読める指示・手順のMarkdownを置き、機械検査する項目はJSONのmanifestへ分ける。共通ルール・同梱ツール・出力形式・依存もmanifestから参照する。具体的な配置名は実装仕様で確定し、暗黙の作業ディレクトリ探索を使わない。

manifestは、形式の識別子、役割IDと説明、指示・手順・同梱コードのパス、必要文脈と出力形式、使用可能なツールと操作種別、作風形式への対応・必須性、必要runtimeとツール契約の互換性を宣言する。内容の版は独自の版番号ではなくGitフルコミットハッシュとする。

モデルは制作会話で選択した値と補助モデル設定から解決し、役割の指示で黙って別モデルへ切り替えない。定義が必要な能力・入力形式を現在の選択モデルやツールが満たさなければ、原因と対処を示して開始を止める。

受付時に固定したコミットから使用パス・blobと依存を列挙し、読み取り専用の実行用領域へ取り出す。未追跡・未コミットの開発ファイル、別のAGENTS・skills・MCP設定・外部参照を暗黙に混ぜない。実際に有効なCodex設定・ツール構成・モデルと要求値を記録し、迂回経路の制限は実装時に検証する。

生成操作スクリプト・一時出力・実行ログは定義と別領域へ残す。共通化の候補ができても自動でmanifestやGit定義を書き換えず、人間の採用・コミット・互換性検査を経る。利用者が初期構築後に定義・ツールを更新する際の検証確認は既存のADR 0002に従う。

## 成果物の構造と工程間の引き継ぎ

操作相談を除く工程の成果物は人間向けの文章だけにせず、既存の文章記録・ファイル参照・保存状態等へ結び付いた構造化項目も保存する。新たな制作履歴の版管理体系を追加せず、既存のIDと参照で関連付ける。

| 成果物 | 保存する主な項目 |
| --- | --- |
| 参考調査 | 出典・確認日・参考にする要素・意図との関係・人間の選択・保持画像と利用条件 |
| シーン計画 | 部品・位置関係・概寸・制作順序・参考資料・仮説とその採否 |
| Blender編集案 | 起点・対象・変更項目・変更理由・素材と依存・プレビュー・保存状態・検査結果・独立した変更と依存 |
| レンダー成果物 | 起点・設定・13レイヤーと形式・色変換・対応する制作データ・出力検査 |
| 振り返り | 対象作品集合と全履歴索引・実参照・事実と理由・仮説・不足・項目別の方針案と採否 |


例えば「海辺のバス停」では、人間が参考資料を選び、シーン計画から屋根・柱・ベンチの構成と概寸を採用する。人間がモデリング工程へ依頼すると、その計画の採用記録・参考資料・制作意図を入力として編集案を作る。人間が保存状態Aを採用した後、植物配置への新しい依頼はAを起点に、選択素材・配置条件と最新の保護指定を取得する。未採用の仮説・別案を採用済みとして渡さない。

未採用の編集案を起点として追加修正する場合は、指定した候補の保存状態を維持し、上記の採用済み本流の引き継ぎと区別する。どの場合も、次工程は人間が選んで依頼する。計画・編集案の完成を工程の自動進行や自動採用の許可にしない。

## 命名・保存用要約の起動

- 命名は最初のLLMを使う依頼の原文を起点にクライアント側で起動し、設定した補助モデルに短い会話名を生成させる。通常の送信や原文・結果保存を待たせない。LLMなしの記録送信では起動しない。
- 会話名がない間は仮の表示名を使う。命名の失敗・停止・上限では未命名として残す。初回の自動命名後は会話の進行で名前を勝手に変更せず、人間の明示した名称変更を尊重する。命名処理中に人間が命名した場合も、後着の自動結果で上書きしない。
- 保存用要約は既存の文脈設計どおり、依頼の完了・停止・確認待ちを区切りとして追加原文を対象にする。ただし人間の停止・利用上限・認証待ちでは新しいLLM処理を起動せず、未要約範囲を保持し、後の明示再開時等に補えるようにする。
- 補助処理のモデル、対象原文IDと範囲、起点依頼、参照、結果、失敗・停止を保存する。要約は保存済み原文へ対応付けて追加し、原文・採否・保護・制作意図を置換しない。Codexの内部圧縮とは独立した処理とする。
