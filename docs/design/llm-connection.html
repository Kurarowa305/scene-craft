1. 担当範囲

実行基盤

仕様
  • 初期からローカル Web アプリを用意し、Codex app-server をエージェント実行基盤として採用する。
  • エージェントの実行処理と文脈管理の自作を減らすことを優先する。
  • ADR 0004 。

制作管理

仕様
  • scene-craft は作品・保存状態・編集案の採否・保護指定・手修正と制作履歴を管理する。
  • Codex の会話と作品の対応を保持する。

工程選択

仕様
工程ごとに人間がエージェントを呼び出す初期範囲を維持する。初期要件

費用

仕様
  • LLM 利用は ChatGPT Pro の契約内とする。
  • 自動補充無効・既存クレジットなしの確認は利用者が行う。
  • ADR 0003 。

停止

仕様
  • 利用上限や人間の停止では途中状態を残して止まり、人間が再開する。
  • LLM を使わない閲覧・手作業の記録・バックアップは継続できる。
  • 初期要件 。

1-1. データの対応

Codexは会話の継続とモデル処理を管理し、scene-craftは独自IDで原文・依頼・制作記録を保持する。接続対応記録で両者のIDを結び、結果を照合する。

  • 一つの依頼が複数turnにまたがる場合も、同じturnで複数の外部操作を行う場合も、実行と再実行を個別に記録する。
  • 発言itemを原文として保存する。
  • LLMなしの記録送信や外部取り込みの原文、通常プログラムの実行は、対応するitemがなくても保持する。Codexの内部継続データを移行しなくても会話IDと保存済み原文は残す。

2. 認証方式

採用判断

仕様
  • Codex 自身の ChatGPT ログインを採用し、ログイン・認証情報の保存・トークンの自動更新を Codex に任せる。
  • エージェント実行・文脈管理と同じく、自作と保守の範囲を減らすためである。
  • ADR 0004 。

処理内容

仕様
  • 自動補充無効・既存クレジットなしを費用面の運用前提とする。
  • アプリによる自動検証や将来の設定変更を含めた課金防止の保証とは区別する。

認証

仕様
比較の根拠は 専用 OAuth を使う app-server 構成 と Codex の認証方式 を参照する。

2-1. 費用条件

費用条件は利用者が確認する。

認証

仕様
API キーの課金経路は、ChatGPT 認証の強制、接続先の固定、API キーや別 provider 設定の混入防止で制限する。
  • ChatGPT認証では契約枠を超えると既存クレジットを消費し得る。
  • 自動補充が有効なら、残高低下による追加購入が発生する。

採用判断

仕様
利用者による自動補充無効・既存クレジットなしの確認を採用判断の根拠とし、契約枠限定の条件は維持する。

2-2. 費用条件の確認

処理内容

仕様
自動補充が無効で既存クレジットがないことは、利用者が確認・管理する。
  • この判断は費用条件の確認を利用者へ委ね、基盤側の確認処理を不要にするためである。
  • ChatGPT Pro の契約内で利用する。

適用条件

仕様
利用情報の表示を設ける場合も、取得できなければ不明として表示し、送信可否の条件とは分ける。

3. 接続契約

接続と復旧では、通信の回復と制作操作の再実行を分けて扱う。

アプリとの通信

合意した契約
  • scene-craft のローカル実行プロセスから stdio で app-server を管理する。
  • 検証では Windows 側の SQLite 保存先で起動に失敗し、WSL 側へ分けると成功した。
  • 製品の保存先は OS の責務設計と合わせる。
  • ブラウザを閉じても実行プロセスが動いていれば維持する 。

会話

合意した契約
scene-craft の会話と Codex thread ID を対応付け、依頼と turn ID、 ツール要求と操作記録を結び付ける。要約・原文・制作状態を区別する

成功判定

合意した契約
終端通知の成功状態を確認して完了を確定する

認証情報

合意した契約
実行環境の専用保管先に保存する。具体的な保管方式は Codex の設定と Windows/WSL の責務設計に合わせる

費用設定の確認

合意した契約
利用者が行う

トークン更新

合意した契約
保存・自動更新を Codex に任せる方針を採用する。scene-craft が扱う再認証の状態と、更新前後の制作操作の重複防止・継続の条件を具体化する

再認証と手動再開

合意した契約
失効・権限不足・一時的な通信障害を区別する。再認証後は途中状態を照合し、人間の指示で制作を再開する

再試行と回数制限

合意した契約
Codex 内部の通信再試行と scene-craft の依頼再実行を区別して記録する。依頼全体で最大2回の再実行予算を管理する

モデルの選択単位

合意した契約
  • 制作会話については、直前のチャットで選択していたモデルを新規会話へ引き継ぎ、会話ごとに変更できる。
  • 使用可能なモデルから選び、実行に使ったモデルを記録する。
  • 初期の既定値は下記のモデル選択を参照 。

ツール

合意した契約
専用stdio MCPを用い、許可された変更範囲・保護指定を制作操作の実行側でも確認する。具体的なツール契約は後続設計へ引き継ぐ

公式の thread/turn 機能、動的ツールの実験扱い、比較した専用 OAuth 案の再起動条件は 比較調査 を参照する。

3-1. 選択単位

会話ごとに利用者がモデルを変更できる。実行に使ったモデルを記録し、選んだモデルが使えない場合は利用者へ変更を求める。モデルの変更は利用者が選ぶ。

3-2. モデル設定

初回

仕様
過去にモデルの選択がない初回のみ、app-server が示す利用可能な既定モデルを初期選択として使う。

新規会話

仕様
  • 新しい会話は直前のチャットで選択していたモデルを引き継いで保存する。
  • 作品作成や振り返り専用会話でも同じ扱いとする。

適用時点

仕様
  • 会話のモデル変更は次の依頼から適用する。
  • 停止した依頼を別モデルで再開する場合は利用者が明示して選び、同じ依頼の再実行回数は維持する。

推論設定

仕様
  • 初期の推論強度は選択モデルの既定値、速度は標準とする。
  • モデル・推論強度・速度の実行設定を記録する。
  • 設定画面の詳細は画面設計で扱う。

3-3. 命名・保存用要約の補助モデル

モデル

仕様
  • エージェント契約の設計で、利用量・コストを抑えるため、命名・保存用要約には制作会話と別のモデルを使うとする。
  • 設定に「命名・保存用要約モデル」を設け、初期値はGPT-6 Luna（gpt-6-luna）、利用者が変更できるようにする。
  • 制作会話のモデル引き継ぎ・会話別選択は引き続き上記の契約に従う。
  • 補助処理ごとに選択モデルと対象を固定・記録する。
  • 未命名・未要約として原文と制作結果を保存する。

4. 送信と停止の境界

送信時は、費用情報の取得と実際の停止条件を区別する。

採用判断

仕様
  • Codex 管理の ChatGPT 認証と採用した接続設定を使う。
  • 認証が必要な場合は再認証を案内する。

停止

仕様
  • 停止要求、受付結果不明、前の実行の未解決状態を確認する。
  • 同じ制作データの実行順と変更範囲は制作操作側でも確認する。

上限

仕様
  • 利用情報の取得失敗と、実際の実行で契約枠の上限に達して停止したことを区別する。
  • 上限到達時は途中状態を保存し、人間が再開する既存要件を維持する。

4-1. 停止・復旧の判断

認証切れ、PC・実行プロセス終了後は、人間の再開指示を待つ。実行済み操作を照合し、実行結果を確定してから継続する。

状況 scene-craft の扱い 再開・再送
Codex 内部で復旧中（error.willRetry=true） 進捗として表示し、同じ turn のイベントを受け続ける 同じturnのイベントと終端を待つ。契約枠上限・人間の停止条件は別途優先する
正常終了 turn/completed.status=completed を確認し、終端と結果を保存する 終端・結果・保存の確認後に完了とする
契約枠の利用上限到達 新しい依頼と制作操作を止め、途中状態を残す 人間の再開を待つ
認証が必要 Codex の通常の更新で回復しなければ、再ログインが必要と表示する 再ログイン・途中状態の照合後、人間が再開する
確定した一時障害による失敗
  • 最終失敗
  • 実行済み操作
  • 残りの再実行回数を確認する
 同じ制作結果を維持でき、重複実行を防げる場合だけ自動再実行する
turn/start の受付結果が不明 ローカルの依頼記録、既知の turn/item、thread/read の履歴を照合する 対応を確定して再送可否を判断する
人間の停止 停止要求を保存し、新しい操作を止め、turn/interrupt を要求する 人間の再開指示を待つ。停止完了前は「停止中」とし、終端不明なら「状態確認が必要」とする
PC・実行プロセスの終了 中断として記録し、再起動後に会話履歴と制作操作の記録を照合する 人間が再開を指示する
一般的な HTTP 429・原因不明のエラー エラー種別と利用枠を取得して原因を分類する 原因を確認して再実行の可否を判定する
保護指定・権限・設定・文脈上限などのエラー 原因と必要な対処を表示し、関連する処理を止める 必要な設定変更と対処を人間が選ぶ

error の受信と turn の終端は別である。終端通知を待つ。通知を受け取れない切断では「状態確認が必要」とする。停止要求と完了通知が競合した場合も、実際に確認できた結果と停止要求を両方残す。

4-2. 再実行

依頼

仕様
Codex 内部の HTTP/ストリーム再送は Codex に任せ、scene-craft が制作依頼をやり直す回数を一依頼あたり最大 2 回（初回を含め最大 3 回）とする。

再実行

仕様
  • scene-craft は元の依頼 ID と累積の再実行回数を保持する。
  • 再実行は最終失敗後に、認証・停止状態、制作状態、同じ結果を維持できることを確認してから行う。
  • デザインが変わる、判断できない、既に何が実行されたか分からない場合は、人間が判断する。
  • 制作操作側でも依頼全体の再実行予算を管理する。
  • モデルが同一 turn 内で制作操作を修正して再度呼ぶ場合も、制作操作側で同じ依頼の再実行予算を確認する必要がある。
  • 何を一回として数え、成功した操作と再実行をどう対応付けるかは、実行状態・順序制御・再実行・復旧を決める と 工程別エージェントの入出力とツール契約を決める で具体化する。
  • 再実行回数は制作操作のやり直しに対応付ける。

停止

仕様
  • scene-craft の接続処理が持つのは、実行前の条件確認、依頼と thread/turn の対応、進捗と終端の記録、停止要求である。
  • OAuth 更新、モデルとツールの往復、文脈圧縮、内部通信の再送は Codex に任せる。
  • 認証情報の実体は Codex 標準の保管機構に置く。
  • OS 資格情報ストアとファイル保管の具体的な選択・配置は、起動 OS と一緒に後続設計で決める。

出力

仕様
検証済みの入出力・画像・会話再開・ツール往復という確認観点を再利用する。

4-3. 異常時の確認条件

接続処理の入口でイベントと取得応答を模擬し、異常時の判断を確認する。

模擬する状況 必ず確認する結果
自動更新通知、利用枠・残高の取得失敗 認証状態と実行条件に従って送信を継続する
ログアウト・認証失効、実行時の契約枠上限到達 認証が必要な状態と上限到達を区別する。上限到達では停止して途中状態を残す
再試行通知の後に成功／最終失敗 内部再試行中の重複送信がなく、終端を一度だけ扱う
受付応答の喪失、遅れて来る通知、履歴との対応不明 依頼・turn/item・履歴を照合して対応を確定する
停止と完了の競合、停止要求後のツール呼び出し 確定した結果を正しく残す
エラー種別・turn が変わる再実行、プロセス再起動 元の依頼の回数を保持する

外部ツールが既に変更した制作データの整合性は、制作操作とその記録を使う別の検証が必要となる。技術上の根拠と限界は 実接続記録の復旧設計補足 に記す。
