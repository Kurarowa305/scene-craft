対象と責務

作品の記録はWSL側SQLite、制作ファイルはWindows側に置く。データモデルは論理的な識別子・参照関係・記録が成立する単位を定める。

制作履歴の節点は保存状態、枝は制作データの変更、採否は特定の編集案・保存状態に対する判断とする。会話・実行・理由は保存状態を説明する記録として保持する。定義・作風の版だけを Git フルコミットハッシュで参照する。

識別と共通契約

  • 下記の契約表に挙げる各概念は、それぞれ永続 ID を持つ。ID は対象の同一性を示す。表示名・保存場所の変更や復元後も同じIDを使う。取り込み時の重複・衝突の扱いは保存設計で具体化する。
  • 記録時刻を必須とし、後日登録で実際の作業時刻が分かる場合は別に記録する。同時刻でも参照関係と確定順を識別できるようにする。
  • 作品に属する記録は作品 ID を持つ。複数作品の振り返りは対象作品集合を持ち、通常の制作依頼の変更先は一作品に限る。
  • 確定済み保存状態の内容・変更元を保持する。理由・要約は訂正元を指す新しい文章記録として追加する。状態遷移・採否変更・現在状態の切替は以前の判断とともに記録する。
  • Git 参照はリポジトリの識別とフルコミットハッシュを持つ。定義と作風は別の参照を持てる。

主要データの契約

各行は、それぞれの ID で独立して識別・参照する一つの概念を表す。例えば、手修正は変更記録の種別、制作会話と振り返り専用会話は会話の用途、変更前・AI結果・修正後は保存状態の役割として扱う。

保存状態の内容と成立

保存状態は、その時点の作品に属する .blend、PSD/PSB、必要な素材、プレビューなどへの固定参照の集合とする。変更していないファイルは前回の固定参照を引き継げる。

PSD が参照したレンダーと、そのレンダーの入力保存状態を結び付ける。レンダーの入力と出力は別 ID で識別する。作品の保存状態に出力を含めるときは新しい保存状態として記録する。

新規作品では、制作データがまだない状態を明示できる。取り込み作品では、登録したファイルを最初の保存状態にし、取り込み前の制作過程は不明とする。人間による後日の補足は補足として保持する。

登録処理の失敗と、確定後に素材の不足・削除が判明したことを分ける。

ファイルの状態は、作成の確定（途中／確定／失敗・不明）と現在の可用性（存在確認済み／未確認／欠落／明示削除／破損）を分ける。現在の可用性と当時の保存状態・採否の事実を分けて保持する。復元可能性は依存素材も含めた確認結果と確認時刻を持つ。

分岐、組合せ、採用

同じ依頼で比較する代替案は同じ基準状態から分岐する。手修正はその候補の枝に追加し、AIへの追加の修正依頼も指定した候補の保存状態から枝を伸ばす。通常の継続では直前の状態を変更前とし、以前の状態を明示して別の修正を試す場合はその状態から分岐する。

未採用の編集案へのAI修正と手修正

未採用の編集案の AI 結果、その案への手修正後、AI による追加修正後のいずれも、保存状態が確定し必要な実体が利用可能なら AI への修正依頼の起点にできる。未採用の案も修正の起点に選べる。Photoshop の自動操作を追加するものではなく、AI が編集する対象は既存の工程・ツールの対応範囲に限る。

人間から「この案をもう少し明るくして」と依頼された場合は、新しい依頼 ID と実行 ID を持たせ、指示原文、修正元の編集案 ID、実際の起点の保存状態 ID、変更範囲・保護指定を固定する。変更記録は「AI編集」とし、指示は依頼、実際の変更者・実効設定は実行に結び付ける。

AI が作った修正結果は新しい編集案 ID と保存状態 ID で記録する。新しい編集案は修正元の編集案を参照する。新しい案の基準は今回指定した状態となり、元の案の基準と異なってよい。同じ選択目的を維持する追加修正では代替案を束ねる識別子を引き継ぎ、修正元の連鎖で最初の案までたどれる。手修正はその時点で対象とする編集案に結び付け、後続の AI 修正もその案と修正済み状態を指定する。

例として、編集案Aの状態A0に対する依頼Q1で編集案A1・状態S1を作り、A1に手修正を加えて状態S2を記録し、依頼Q2でA1・S2から編集案A2・状態S3を作れる。A2はA1、A1はAを修正元として参照する。最後の採否はA2・S3を対象とし、最初の案と途中の修正理由・指示は残す。採用・適用の成功後に作品の現在状態を更新する。

候補の修正では指定した保存状態を起点として維持する。実行直前には指定状態の可用性、変更範囲・保護、同時編集の有無を確認し、現在の制作状態へ反映できるかは採用時に改めて照合する。案の基準と作品の現在状態が異なる場合の適用・競合処理は編集案設計へ引き継ぐ。

追加の制作指示と、失敗・停止した元の依頼のやり直しを区別する。完成した候補への新しい修正指示は新しい依頼として記録する。修正依頼自体が失敗した場合は、その依頼の再実行予算を使う。「失敗した処理をもう一度」「停止した処理を再開」は人間からの指示でも元の依頼 ID と累積回数を維持する。

選択と組合せ

同じ目的の代替案の一回の選択では一つの状態を選ぶ。変更した判断を追加する。採用されなかった他の案は未選択として残す。

植物配置と照明調整のような独立した変更は別々に採否を判断できる。複数の案を組み合わせたときは、実際の変更前後の保存状態と採用に寄与した案・保存状態・判断を記録する。内容の出典を示す参照にする。元の案全体を採用したか、一部を取り込んだかも区別する。組合せ結果を確定して現在状態を更新する。

組合せ・競合の扱い、部分採用の具体的な単位、採用後の他案への切替方法は編集案設計に従う。

復元と派生

復元では、戻す直前の作業状態を記録したうえで、新しい保存状態を作る。変更記録は変更前と復元元を別々に参照する。新しい状態の内容は復元元に対応するが、後から行った復元という事実は残る。

派生作品は新しい作品 ID を持ち、元作品 ID と起点の保存状態 ID を記録する。派生先の最初の保存状態を別に確定し、以降の現在状態・会話・採否は別作品に属する。出典として参照する。取り込んだ制作意図や作風も、その時点の参照を明記する。

グラフの関係には、変更前、組合せへの寄与元、復元元、派生元という役割を持たせる。新しい状態から既存の状態を参照する。現在採用している状態の参照はグラフとは別に持つ。

会話、共有情報、原文と要約

制作会話は一作品に所属する。制作意図、現在採用している状態、採否と手修正、保護指定、固定した作風は作品単位で共有する。ただし実行時には、実際に使ったこれらの参照を固定して残す。現在状態を起点にする待機依頼は実行直前に最新の状態を確認する。候補の保存状態を明示した修正依頼はその起点を維持し、最新の共有情報・保護指定との整合性を確認する。前提が変わった場合の確認は実行状態設計で具体化する。

会話の要約は要約対象のメッセージ ID／範囲と作成者・時刻を持ち、原文と独立して残す。訂正時は新しい文章 ID を持つ。一依頼が複数 turn に対応する場合も、同一 turn 内で複数回制作をやり直す場合も記録できる対応関係にする。

複数作品の振り返り専用会話は対象作品集合を保持し、実際の分析は参照記録で入力を固定する。一作品の振り返りにも同じ参照記録を使う。作風の傾向という仮説と、人間が採用した制作方針を別の内容として識別する。分析結果には根拠を残し、採用された変更を Git へ記録してから作品が参照する。作品への作風更新は人間が選び、旧参照と新参照を残す。文脈の選び方は文脈・作風設計の範囲とする。

実行、Windows の記録、エージェント改訂履歴

実行時の記録には、使用した定義・作風の Git 参照、工程、モデル、推論強度・速度、指示・ツール・手順への参照、入力状態を保持する。手修正・取り込み等で AI 定義を使用していない場合は「適用なし」、過去の取り込み元で分からない場合は「不明」と区別する。

依頼ごとの自動再実行は最大2回という既存契約を維持する。再起動・turn変更・原因変更後も累積回数を維持する。人間による停止や利用上限到達後は、人間の再開指示を待つ。

AI 実行から Windows 実行への親子関係を残し、Windows 側の開始・停止・完成記録は実際の Windows 実行 ID と要求の世代で照合する。同じIDの通知は、対応する制作操作へ照合する。

Blender連携設計で要求する入力／出力ハッシュ、Blender 版、エンジン・デバイス、カメラ・フレーム・解像度・seed・サンプル数、色管理・ICC、パスの意味・変換、ID 色対応、深度範囲、Shadows 設定、依存素材、操作スクリプトの実体またはハッシュと保持先を、制作実行・生成物のメタデータとして保持する。完成出力とチェックポイント、欠落・停止・失敗を区別する。

エージェント改訂履歴は定義等の変更コミットと理由を正として参照し、それを使った実行へ結び付ける。モデル設定だけの変更も、実行ごとの実効設定と設定変更の記録・理由から追跡できるようにする。場当たり的に生成した操作スクリプトの修正も定義そのものの改訂と区別する。

記録が成立する単位と不変条件

  1. 保存状態の構成、変更記録、確定したファイル参照の対応が揃って初めて、その変更を完成した枝として公開する。内容の同じ状態でも復元等の由来が異なる記録は別 ID を持てる。
  2. AI 案の基準・AI 結果・修正元の案は同じ作品に属する。候補への修正依頼で指定した起点と実行入力・変更前・新しい編集案の基準を一致させ、起点が修正元の案またはその案への手修正に由来することを検査する。手修正とAI修正を交互に重ねても採否対象から元の案まで追跡できることを検査する。組合せの場合は寄与元と最終結果の関係を明示する。
  3. 採用判断の受付と制作状態への適用成功を区別する。判断と適用状態を保持し、適用成功後に現在状態を更新する。
  4. 現在状態の更新記録と現在状態の参照更新は DB 内で一体として確定する。作業 ID を用いた照合・復旧方法は保存・実行状態設計で決める。
  5. 理由は任意で、手修正・採否と制作を継続できる。後日の入力・訂正は対象と記入時刻を保持する。
  6. ファイルの削除・欠落後も節点・変更・採否・文章・出典のIDを保持する。復元・派生・実行に必要な実体が不足した場合は不足を示す。
  7. 外部通知や登録要求の再送は、同じ記録へ照合する。人間が明示的に再度行った別の作業と区別する。具体的な受付キーと保持期限は実行状態・保存設計で決める。

ブランチグラフによる制作履歴の表示

以下は保存状態の具体例を節点として並べた制作履歴であり、概念間の関係図とは別に、同じ概念に属する複数の状態を表示する。節点は保存状態、枝は変更記録、採用の表示は採否記録に対応する。手修正は種別が「手修正」の変更記録として表す。

採用だけの場合は、採否記録と現在状態の更新を残す。AI 修正では指示者が人間、実際の変更者が AI であることを区別する。

節点・枝から、変更要約、実行または手修正の変更記録による由来、変更理由、採否と採用理由を ID で取得できるようにする。判断した時点ごとに取得する。理由が未入力なら未入力と分かる。ホバーの見せ方、長い履歴の省略、復元線・派生線の描き分けは画面設計で決める。

場面 記録の例 確認できること

修正依頼の待機と失敗 Aの状態を指定して修正依頼が待機中に別案Bを採用。指定したAの状態は維持して整合性を確認。修正依頼が失敗したら同じ依頼として再実行 指定したAの保存状態を起点に維持する。追加の制作指示と失敗の再実行を区別する
