責務

Codex app-server は同一threadの継続・再開と、モデルが扱う会話履歴の圧縮を担当する。接続設計に従い、scene-craftで独自の圧縮ループを実装しない。

scene-craft は原文・要約・制作履歴を保存し、作品の共有情報と依頼に関係する記録を実行へ渡す。別会話への引き継ぎ、振り返りの根拠、バックアップからの再開は、Codex内部の圧縮内容だけに依存させない。

処理 担当と境界
同じ会話の続行 Codexの既存threadを継続・再開する。scene-craftの要約だけで毎回新規threadを作る方式にはしない
モデル文脈の圧縮 Codexに任せる。scene-craftの依頼の完了・停止時に必ず圧縮が走るという前提は置かない
作品共有情報の取得 scene-craftが最新の確定情報を取得し、実行に使った参照を固定する
保存用・他会話参照用の要約 scene-craft側の処理。対象原文の参照を持ち、Codexの内部圧縮とは独立して保存する
根拠の追加取得 許可された作品・対象範囲の要約・原文・履歴を必要に応じて取得し、参照を残す

app-serverのthread/resumeとthread/compact/startは公式OpenAI documentationに記載されている。公開されるcontextCompaction項目を、作品の根拠付き要約本文としてそのまま保存・再利用できる契約とは扱わない。既存の実接続検証では圧縮後の継続を確認したが、長期の制作履歴保持や別会話の共有は保証していない。

共有情報と制作意図

  • 制作意図、現在採用状態、採否と手修正、保護指定、固定した作風は作品単位を正とする。会話ごとのコピーやAIの要約で上書きしない。
  • 「夕景もいいかも」は検討中の案。「この作品は夕景に変更して」のような明示的な指示を共有する制作意図の更新根拠にできる。明示した更新に重ねて同じ確認を強制しない。
  • 更新時は指示原文と新しい文章記録を関連付け、訂正前の意図・記入者・時刻も維持する。単なる提案・仮説を人間が確定した意図へ変換しない。
  • 制作方針より作品の制作意図を優先する。過去の傾向だけを理由に新しい依頼を拒まない。
  • 「静かな夜景」の作品で「昼のように明るくして」と頼まれ、両立する調整か意図の変更か判断できない場合は確認する。制作意図の優先を、変更範囲や保護指定を越える許可にはしない。

実行に渡す文脈

  1. 対象作品、依頼原文、実際の起点となる保存状態、制作意図、保護指定と依頼限定許可、変更範囲、採用済み状態、固定した作風の参照を取得する。未選択・未入力・制作データ未作成は明示し、推測で埋めない。
  2. 同じ会話の継続はCodexのthreadを利用する。作品の最新情報はscene-craftの確定記録から補い、古い会話の記述を現在値と誤認させない。
  3. 同じ作品の他会話から依頼に関連する要約を選ぶ。必要な原文・採否・手修正・画像等を追加取得できるようにし、参照元を追跡可能にする。他作品の制作会話を無条件で混ぜない。
  4. 実行へ渡した文章・保存状態・採否・変更・ファイル・要約と、その要約の対象範囲を記録する。定義と作風はそれぞれのGit参照・使用内容を残す。追加取得も実行に関連付ける。

待機依頼は実行状態設計に従い開始直前に最新の共有情報を確認する。明示した候補の保存状態を最新採用状態へ差し替えない。前提が合わなくなれば確認する。実行の途中で更新された情報を過去の入力へ遡って反映しない。

必須情報を省いて実行可能に見せない。長い履歴は関連範囲を分けて取得し、要約に未反映の原文も参照対象にする。必須情報自体を扱えない場合は原因を示して停止し、必要な対処を求める。モデルの自動切替は行わない。

要約の更新と原文

  • 依頼の完了・停止・確認待ちを更新の区切りとし、追加された発言を要約する。要約は履歴の補助であり、制作操作の成功・採用・停止を確定する根拠にはしない。
  • 要約は対象メッセージID／範囲、作成者・時刻、根拠の参照を持つ。訂正時は新しい文章記録を作り、訂正元を残す。原文を置換・削除しない。
  • 次の実行では最新の共有情報、利用可能な要約、要約に未反映の原文を区別する。古い要約の作成後に確定した採否・意図・保護指定を要約で巻き戻さない。
  • 要約失敗や中断時も原文・依頼・途中結果を保存する。未要約の範囲と失敗を示す。受信途中・欠落は完全な原文と区別する。
  • 要約処理のLLM呼び出しにも既存の認証・利用上限・停止契約を適用する。人間の停止後に新しい要約処理を勝手に起動せず、未要約として残せる。要約の具体的な工程契約はエージェント設計へ渡す。

振り返りと根拠

人間が一作品または複数作品を選んで起動する。複数作品の場合は専用会話として対象作品集合を保持する。対象範囲は各対象作品の全履歴とし、採用状態・保存状態で絞らない。開始画面に履歴範囲の選択項目を設けない。全履歴を対象とすることと、実際に分析で取得・観察できた範囲の説明を区別する。

  • 完成・採用された結果に加え、不採用案と手修正の比較も使う。未選択の案を不採用と解釈しない。
  • 実際に参照した作品・保存状態・採否・変更・文章・ファイルを振り返りの参照記録へ固定する。参照対象と分析できた範囲を示す。
  • 結論には具体的な根拠を付ける。記録された事実、人間が明示した理由、AIによる解釈・仮説を区別する。理由未入力を人間の意図として補わない。
  • 画像や制作実体が削除・欠落していれば、その実体を観察したと主張しない。残る文章・プレビュー等で分析した範囲と限界を示す。
  • 後日理由が補記・訂正されても過去の分析と根拠は上書きしない。根拠の文章記録等に更新があれば「根拠に更新あり」と示し、人間が起動した再分析で新しい記録を参照する。

作風の傾向から制作方針へ

振り返り結果には作風の傾向を仮説として示す。人間は項目ごとに採用・編集・保留を選べる。「暖色が多い」という観察を「主役を暖色で際立たせる」という方針へ編集できる。観察された頻度を必須ルールへ自動変換しない。

元の仮説・根拠、人間が編集・採用した内容と判断を追跡可能にする。保留した仮説と採用済みの制作方針を同じ扱いにしない。理由がなければ未入力とする。

採用した変更をGitへコミットし、作品への適用は別に選ぶ。通常制作では選択した版の採用済み制作方針を使い、未確認の作風の傾向は振り返り・方針の検討時に参照する。

新しい作品は作風の版を選ぶか、作風なしで始める。前作の版は候補として提示できるが自動適用しない。派生開始時も参照元と派生先の選択を区別する。

作品の版更新はGit版管理設計に従い、旧・新参照、選択者・時刻・理由を保持する。定義と作風で異なるコミットを使える。待機中に作風が変わった場合は開始前に旧版継続／新版切替を確認し、自動再実行では版を維持する。コミット失敗・非互換・欠損を、採用・適用完了として扱わない。

会話履歴の取得

paginated履歴はページングで取得する。Codexの要約itemを完全な原文として保存しない。保存済み原文を正とし、実行・分析で使った参照の固定と、制作意図・方針の明示更新を維持する。
