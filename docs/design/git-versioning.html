Gitの版固定と更新

何を使ったかを、コミットで示す

定義と作風の版はGitを正とする。受付時のコミットを固定し、使ったファイルのblobと実行時の設定・runtimeを追跡する。

責務と前提

  • ADR 0001・ADR 0002を前提とする。定義・作風の版の正はGitフルコミットハッシュ。作品・実行・保存状態のIDとは区別する。
  • 定義と作風は同じリポジトリに置き、別々のコミットを参照できる。「作風の傾向」と採用済みの「制作方針」を別の内容として扱い、作品の制作意図を優先する。
  • 版管理はコミットの解決・保持・内容の取り出し・互換性確認を担当する。実行管理は受付・停止・順序・再実行予算、保存はDB・制作ファイルとの整合性とバックアップ全体、エージェント契約は定義の具体的な構造を担当する。
  • 過去の内容を読み出せることと、当時の環境を復元して同じ結果を生成できることは区別する。後者は初期要件に含めない。

ローカル記録の参照契約

記録 保持する情報
Git参照 リポジトリ識別、Gitオブジェクト形式、フルコミットハッシュ、対応する保持用タグ。ブランチ名・表示名用タグは任意の表示情報
使用内容 定義・作風それぞれのGit参照、使用したエントリ・パスとGit blob識別子。作風未選択を明示
依頼 受付時の使用予定参照、版の選択・切替の記録。受付の二重送信でも選び直さない
実行 実際に使用した参照、互換性確認結果、実効モデル設定・外部ツール版・実行環境の記録への参照
作品の作風更新 旧参照・新参照、選択者・時刻・理由。以前の実行は書き換えない
保持・リモート保存 保持用タグ、ローカル可用性、保存先のリポジトリ対応、リモート一致の最終確認時刻・結果。未保存・確認不能・欠損を区別

リポジトリ識別は保存場所・remote URLから独立した永続IDとし、バックアップ・復元で維持する。復元先のcloneは保存元のリポジトリ識別へ対応付け、異なるリポジトリへ暗黙に置き換えない。保存場所の移動で過去参照を作り直さない。オブジェクト形式とスキーマ識別は内容の独立した版番号ではない。

定義・作風の使用版について、ローカルで作った保持用タグを、そのまま同名・同じ対象コミットのタグとしてGitHubへpushする。ローカル用・リモート用に別の保持参照は作らない。使用内容の識別にはコミットハッシュも残し、保持用タグと両方を記録する。表示名用タグの併用は任意だが、参照済みコミットの保持用タグは必須とする。

「適用なし」「未選択」「不明」「参照先欠損」を区別する。手修正や取り込みに現在の定義ハッシュを付けて、使用したように記録しない。モデル等の実行時選択は、Gitの既定設定と区別して実効値・変更理由を記録する。モデル選択だけの変更にGitコミットを強制しない。

依頼受付・開始・切替

  1. 通常制作では利用者が採用した定義の既定コミットと、作品に固定した作風を受付時に解決する。既定定義の変更は以後の依頼から適用し、単にmainやブランチ先端が進んだだけでは既定値を切り替えない。試行は変更ブランチのコミットを明示し、制作データのコピーを使う。
  2. ローカルの保持用タグと必要なGitオブジェクトの存在を先に確定し、その後、使用予定参照を依頼と一緒にDBへ保存する。コミットを取得・保持できなければ実行可能な受付を完了させない。受付失敗は原因を残し、LLM・制作操作を開始しない。
  3. 開始直前に制作データ・保護指定・変更範囲を確認する。固定した定義・作風を現在のHEADへ解決し直さない。作品の作風参照が受付時から変わっていれば、旧版で続けるか新版へ切り替えるかを確認する。回答後にも前提を再確認する。
  4. 自動再実行・通信再送は版を維持する。人間による切替は動作中の操作と未解決の開始許可がなくなった後に行う。同じ依頼IDと累積回数を維持し、旧・新参照と理由を残す。通信再送で同じ試行IDの内容を変更しない。未送信を含めて既存の試行がある場合は先に照合し、切替後の実行・試行を別に対応付ける。
  5. 版を選び直しただけでは再実行回数を消費しない。失敗・停止した操作をやり直す開始予定記録で、実行状態設計どおり消費する。上限を切替でリセットしない。完了済み結果を再利用する場合は、新旧の定義・作風と依存条件の整合性も確認し、旧結果を新版で生成した扱いにしない。

古い作風で一依頼を続ける選択は、その依頼の入力の例外であり、作品全体の固定作風を旧版へ戻す操作にはしない。依頼内の明示切替も、作品の作風の現在値を変える操作とは分けて記録する。

保持用タグとGitHubへの保存

既存の定義・作風リポジトリに保持用タグを作る。専用の保持用bareリポジトリは設けず、通常のローカルリポジトリとGitHubのremoteを使う。Gitのためのbundle書き出しは初期版の必須機能にしない。

  • タグは refs/tags/scene-craft/retained/<full-commit-hash> とし、対象コミットを直接指す軽量タグとする。タグ名は保持のための参照であり、ローカル記録の版は引き続きフルコミットハッシュとする。
  • 作風の作品への選択、依頼受付、版切替などのDB確定前に作る。コミットと使用内容の存在を確認し、履歴や使用内容の欠けたshallow／partial状態を保持完了として扱わない。
  • git update-ref の未作成確認付き操作等で作成する。既存の同名タグが同じコミットを直接指せば再利用でき、異なる対象・symbolic ref等なら上書きせず停止する。アプリは保持用タグを移動・自動削除しない。
  • 本流、未統合、不採用、失敗、待機中の依頼を区別せず保持する。試行ブランチを削除する前に保持用タグを確認する。参照済みコミットをrebase／squashで置き換えず、元コミットを保つマージを使う。
  • タグ作成をDB確定より先に行う。タグ作成後にDB保存が失敗すれば余分なタグを残せるが、参照先を保持できないまま実行可能な依頼を確定しない。起動・保存状態の確認時にはDB参照とローカルのタグ・オブジェクトを照合する。
  • リモート保存は人間が明示的に公開する操作とし、対象の保持用タグをGitHubへ明示的にpushする。通常のブランチpushやmainへの統合だけでは、保持用タグの保存確認を済ませた扱いにしない。無関係なタグの一括pushやforce pushを標準操作にしない。
  • push成功後にリモートの同名タグが記録ハッシュを直接指すことを照合し、保存先と確認時刻を記録する。同じ対象なら再送は冪等に扱い、不一致なら上書きせず停止する。認証・通信失敗や結果不明は未確認として残す。
状況 制作と表示
ローカルのタグ・使用内容が揃い、未push 制作可能。「リモート未保存」と表示
リモートのタグと対象コミットの一致を確認 「リモート保存済み」と最終確認時刻を表示
接続できず現在のリモート状態が不明 最終確認結果と現在確認不能であることを区別。ローカルが揃えば制作可能
ローカルの参照先が欠ける 該当する実行を止める。GitHubから同じコミットを復旧できるか確認
リモートのタグが欠損・異なる対象を指す 保存済みと扱わず不足・不一致を示す。ローカルの履歴・タグを自動変更しない

ローカルコミットと公開は別操作という既存合意を維持する。オフラインや未pushを理由に、ローカルで成立している制作を禁止しない。pushでは未統合コミットやその祖先の内容も送られるため、公開先の可視性を含めて通常の公開確認に従う。制作履歴・資格情報・Codex保存領域をGitへ混ぜない。

保持用タグはローカルのGC後も到達可能にするための参照であり、同じディスク内でデータを複製するものではない。GitHubへの保存はPC故障・移行への備えとする。GitHub上のリポジトリ・保持用タグの削除やアクセス喪失まで耐える独立バックアップ、保持タグの削除防止設定の自動管理は初期の必須範囲に含めない。アプリ外からのタグ削除・移動が起きた場合は照合で不足を示す。

コミット内容の取り出しと実行

  • 使用対象のパス一覧を確定し、コミットのtree／blobから取り出す。git cat-file 等でオブジェクトを直接読み、開発用作業ツリーの未コミット・未追跡ファイルを混ぜない。export用属性で内容が除外・置換され得るarchiveを、そのまま実行内容の正にしない。
  • 定義と作風は別領域へ取り出し、同じ相対パスでも上書き合成しない。定義が読み込む指示・手順・同梱ツール等も固定対象に含める。外部パスへのリンク、欠けたsubmodule・LFS実体等は未解決依存として扱い、暗黙に開発用ファイルを読む代替経路を作らない。
  • 専用領域は実行からの書き換えを禁止し、生成スクリプト・ログ・制作出力は別の実行領域へ保存する。取り出し時に使用パスとblobを照合し、キャッシュを再利用するときも内容の一致を確認する。不一致なら使用せず、保持用タグが指すオブジェクトから再構築する。
  • Codexの設定やツール探索が、固定した領域を迂回して別の指示・ツールを読み込まない契約をエージェント設計へ渡す。scene-craft専用のCodex保存領域だけでこの一致を保証したとは扱わない。
  • 定義内に同梱するツールはそのblobまで固定する。Node、Codex、Blender、ライブラリ等の外部runtimeは実際の版・設定を記録して互換性を確認する。Gitコミットだけで外部実行環境まで固定したとは扱わない。
  • その場で生成した操作スクリプトは実体またはハッシュと保持先を記録し、恒久的な定義の改訂とは分ける。Git管理の定義そのものを直す場合は人間の採用・コミットを経る。

定義・作風・現在環境の互換性

定義側の要求、作風側の提供形式、実行基盤側が扱える契約を検査する。契約の識別子は形式・必須項目を判別するためのもので、作風内容の版は引き続きGitコミットで識別する。

状況 扱い
別コミットでも必要な形式・項目が揃う 利用可能。異なるコミットという理由だけでは拒否しない
作風未選択で、定義が作風なしに対応する 作風なしと記録して利用可能
作風必須だが未選択、必須項目不足、未対応形式 制作操作前に止め、原因と選べる対処を示す
古い定義が現在のツール契約・runtimeに非対応 コミットを閲覧できても実行しない。互換性のある定義・環境を人間が選ぶ
Git参照先が欠損・破損 欠損を示す。バックアップ等から同じコミットを復旧するまで代用しない

作風を新形式へ直す場合は変更案を人間が採用してコミットし、別途作品への適用を選ぶ。互換性対応を理由に作品の固定参照や過去の実行記録を書き換えない。内容の表現としての適切さは形式検査では保証できず、人間の採否に属する。

ローカル保存形式の変更

DB・ローカル記録・バックアップ形式のスキーマ識別と、定義・作風のGit版を分ける。アプリのGitコミットを戻してもDBが元の形式に戻るとは扱わない。

  1. 書き込み開始前に保存形式を検査する。未対応の新しい形式には書き込まない。安全に読める契約がある範囲だけ閲覧を許し、解釈できない内容を推測しない。
  2. 旧形式に移行経路がある場合は対象・変更内容・必要容量・退避先を示し、人間の確認を待つ。確認しなければ移行も新形式での書き込みも始めない。
  3. 実行中の制作操作・他の書き込みを安全に止め、変更するDB・ローカル記録等の移行前状態を退避・検証する。退避の保存・検証が失敗したら移行を始めない。DBだけの変換で制作ファイル全体やGit履歴を毎回複製することは要求しない。
  4. 永続ID、Git参照、理由の訂正履歴を保って変換する。変換後の整合性を検査してから利用を開始する。途中失敗・アプリ終了時も元へ戻せるよう、移行段階と退避先を保存する。
  5. 失敗時は成功扱いで開かず、退避した元データを保持して復旧を案内する。新旧データを混在させて継続しない。成功後も移行前バックアップを自動削除しない。

制作ファイル本体を保存形式の変更だけで一律に再生成しない。旧アプリへ戻す際は、必要なら旧形式のバックアップも復元する。移行後に追加した制作記録を失い得る復元は、その影響を示して別の明示操作とする。物理的な退避・復元方式は保存設計へ渡す。

制作データのバックアップとGitの復元

制作ファイル・依存素材・会話・制作履歴DBの一括書き出しと復元は引き続き必要とし、通常プログラムで実装する。Gitデータの実体はGitHubへ保存し、初期の一括書き出しには含めない。保存設計へは次の情報を渡す。

  • リポジトリ識別、資格情報を含まないGitHubリポジトリの所在、Gitオブジェクト形式。
  • 作品の固定作風、依頼の使用予定版、全実行、旧・新の切替等が参照するフルコミットハッシュと保持用タグ。成功・採用分だけに絞らない。
  • 書き出し時点で確認できたローカル可用性、リモート保存の最終確認結果・時刻、未保存・欠損・確認不能の情報。

制作データを書き出せても、未pushのGit内容まで別PCで復元できるとは表示しない。未保存分があっても制作データの書き出しは可能とし、Git参照先の不足を明示する。認証情報はバックアップへ含めず、新しい環境で別途認証する。

復元先では登録したGitHubリポジトリをclone／fetchし、必要な保持用タグを明示的に取得する。cloneの既定動作に依存せず、対象タグ、フルコミットハッシュ、使用内容の存在を照合する。既存の同名タグが別の対象ならforceで上書きしない。欠損やネットワーク不通ならGit内容は未復旧とする。復元済みの制作記録の閲覧・手作業の記録は続けられ、欠けた定義・作風を必要とする実行だけを止める。Git復旧やアプリ起動だけで制作を自動再開しない。

ローカルにしかなかったコミットは、ローカルデータを失えばGitHubから復元できない。この制約を未保存表示として明示することで、公開を別操作とする運用を保つ。GitHubに依存しないGit実体の一括書き出し、毎回の空リポジトリへの復元検査、作品別の最小Gitオブジェクト抽出は初期版では実装しない。制作データのバックアップ全体の整合性、部分復元・表示の導線は保存設計で定める。
