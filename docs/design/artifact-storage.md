# 制作データの保存・復元・バックアップ

[設計 Issue](https://github.com/Kurarowa305/scene-craft/issues/6)。2026-10-18、利用者と3ラウンドのすり合わせを行い、管理下へのコピー、保存状態の固定、復元・派生・削除、停止後の全体バックアップ、空の保存先への復元、Codex内部データを移行しない方針と失敗時の扱いを合意した。設計の完了であり、製品実装・実機検証の完了ではない。

## 責務と保存単位

[全体設計](application-architecture.md)に従い、制作履歴・会話・依頼等のDBはWSLのLinuxファイルシステム上のSQLite、制作ファイルとWindows側の実行記録はWindowsへ保存する。保存モジュールが保存ルートID・相対パスと各OSの実パスの対応を管理する。移行先ではルートを設定し直し、永続IDや制作の参照関係を維持する。

| 対象 | 保存契約 |
| --- | --- |
| .blend、PSD/PSB、プレビュー | 人間が保存・登録した内容を管理領域へコピーし、ファイル参照・サイズ・ハッシュを固定する。元ファイルを上書きしない |
| テクスチャ、リンク素材、必要なキャッシュ | 依存先の依存も含めて取り込み、管理下のコピーを参照させる。取り込めないものを不足として明示する |
| 保存状態 | 制作ファイル・素材等への固定参照の集合。確定済みの構成・内容を上書きしない。変更しない固定参照は引き継げる |
| 会話・制作履歴 | 原文、要約、理由の訂正前後、採否、変更・復元・派生の由来を独立した記録として保持する。Codex内部状態だけに依存しない |
| 生成物・実行の根拠 | 完成したレンダー・中間EXR、操作スクリプト、実行ログ・実行記録、検証済みチェックポイントを保存する |
| 作成途中の一時ファイル | 完成出力や検証済みチェックポイントと区別し、復元・バックアップ対象に含めない。存在をもって成功としない |
| 定義・作風のGit内容 | 制作バックアップとは分離し、GitHubの保持用タグから復旧する。参照情報と保存状況は制作バックアップへ含める |

作業用のコピーと、記録した保存状態の固定実体を分ける。人間もAIも作業用コピーを編集し、その結果を新しい保存状態として登録する。確定実体を編集用ファイルへのハードリンク等で共有し、編集が過去の保存状態へ伝わる構造にしない。重複排除は必須とせず、採用しても固定内容と削除保護の契約を維持する。

PSD/PSBが参照したレンダーと、その入力保存状態を記録する。Blenderの変更だけでPSDを更新済みとは扱わない。出力を過去の入力保存状態へ後付けせず、新しい保存状態として確定する。

## 依存素材の取り込み

1. 元ファイルと依存関係を確認し、依存先も再帰的に収集する。同じ参照を繰り返し処理せず、循環や未解決の参照を検知する。
2. 素材を管理下へコピーし、作業用コピーの参照先を管理下の素材へ変更する。外部ライブラリの元データは変更しない。ルートからの逸脱、リンクの実際の参照先も確認する。
3. 元の所在と取り込み後のファイル参照、ハッシュ、出典・利用条件等の記録への対応を残す。依存素材の必須メタデータとサービス別の取り込みは[参考調査・素材の設計](reference-and-assets.md)を参照する。
4. コピーした内容と参照先を検証する。コピー中の変更、容量不足、読み取り失敗等で一貫した内容を取得できなければ、その登録を完成扱いにしない。

取り込み不可・所在不明の素材は、不足の対象・理由・必要な操作を記録する。アドオン・実行環境など制作ファイルだけで保存できない依存も必要条件として記録する。別素材への自動差し替えで成功させず、完全復元可能とは表示しない。外部実行環境の完全な復元は初期対象外とする。

必須の制作ファイルのコピー失敗と、外部依存の不足を区別する。後者は不足一覧を持つ保存状態として記録できるが、その不足が必要な制作操作は開始しない。

## 保存の確定と照合

WSLのDBとWindowsのファイルは一つのトランザクションにならない。以下は実装へ渡す確定手順とする。

1. 保存操作ごとにID・受付キー・対象・入力参照・予定先・進行段階を記録する。同じキー・同じ内容の再送は同じ操作を照合し、異なる内容は拒否する。再送のたびに保存状態を増やさない。
2. 一時領域にコピーし、必須ファイル・サイズ・ハッシュ・依存関係を検証する。Windows側には操作IDとファイル一覧に対応する完成記録を残す。
3. 固定実体の配置・完成記録とDB側の構成を照合してから、保存状態・変更記録を公開する。現在状態を切り替える操作では、更新記録と現在状態の参照更新をDB内で一体として確定する。
4. 途中終了・通知の欠落後は、操作ID・完成記録・実体とDBを照合する。ファイルがあるだけで採用・現在状態の切替を推測しない。照合できない操作は失敗・状態不明として保持し、新しい競合操作を開始しない。

ファイル確定後にDB保存が失敗した場合も、その実体を照合対象として保持する。未完了データを完成した保存状態に見せず、履歴・根拠を自動削除して帳尻を合わせない。実行の試行ID・世代・所有権と結果の一度だけの登録は[実行状態設計](execution-lifecycle.md)に従う。

受付キーの保持は、未完了の操作と確定済み記録を誤って二重登録しないことを満たす。具体的なテーブル・キー生成・保持方法は実装仕様で決める。

## 保存状態への復元と派生

### 過去の保存状態へ戻す

1. 人間がBlender／Photoshopの内容を保存し、未登録の手修正を記録する。保存済みデータが対象であることを示して保存を確認する。GUIの未保存内容を自動取得・検出できるとは扱わない。
2. 復元元の制作ファイル・依存素材を確認する。不足・破損があれば、その状態への復元を止める。復元前の記録自体が失敗した場合も切り替えない。
3. 別の作業領域に復元用のコピーを準備し、依存参照を含めて検証する。直前の作業用データを準備段階で上書きしない。
4. 復元元の内容に対応する新しい保存状態と変更記録を確定し、変更前・復元元を別々に参照する。成功後に現在状態を切り替える。失敗時は直前の状態を保つ。

復元元より後の履歴や理由は消さない。後続の手修正を維持しつつ、過去のAI編集だけを選択的に取り消す機能は初期対象外とする。

### 派生作品

元作品ID・起点の保存状態IDを記録し、新しい作品IDと最初の保存状態を作る。必要な素材も含めて独立した編集用コピーを準備・検証する。固定実体の参照を内部で再利用する場合も、編集と削除が元作品に影響しない契約を守る。不足する実体が必要なら派生を開始しない。

元作品の会話・採否・理由は出典として参照し、派生先での発言・判断として複製しない。以後の現在状態・会話・採否は派生作品に属する。

## 可用性と明示削除

[データモデル](domain-data-model.md)に従い、作成の確定状態と現在の可用性を分ける。可用性には存在確認済み・未確認・欠落・明示削除・破損を持たせ、確認時刻を記録する。保存状態の制作実体を復元できることと、Git・runtimeを含む制作実行が可能なことも区別する。

| 状況 | 扱い |
| --- | --- |
| 必要な制作実体と依存が確認済み | 対象の復元・派生に利用できる。制作実行には別途定義・作風・環境の検査が必要 |
| 外部依存の不足・未確認 | 不足と確認状況を表示し、完全復元可能としない。必要とする操作を止める |
| 明示削除・欠落・破損 | 履歴は残す。影響する保存状態と実体を示し、必要な復元・派生・制作操作を止める |

人間は、使われていない候補や過去状態の大容量実体を明示的に削除できる。削除対象の状態自身がその実体を参照することだけで削除不能にはしない。ただし、現在採用中・実行中の対象、または削除対象以外の保存状態・作品が必要とする実体は保護する。依存素材の共有も参照先まで調べる。

削除前に対象・影響する保存状態・復元できなくなる内容を示す。削除開始前に参照・実行状況を再確認し、競合する採用・実行・保存操作と直列に扱う。削除途中の失敗は再照合し、実体が残る場合と既に消えた場合を区別する。会話、採否、理由、変更記録、分岐、ファイル参照のIDと当時のハッシュは削除しない。自動的な容量整理は初期機能として追加しない。

## 全体バックアップの形式と手順

初期版は全作品・全会話・制作履歴・保存対象の実体を、一つの通常フォルダーへ非圧縮で書き出す。作品選択による書き出し、既存データへの合流、差分バックアップは初期必須範囲に含めない。LLMやCodex接続なしで通常のプログラムとして動作する。

以下は論理構成であり、ファイル名・スキーマ・配置の詳細は実装仕様で固定する。

```text
バックアップフォルダー/
├── 構成一覧（形式識別、ID、参照、サイズ、ハッシュ、不足一覧）
├── 制作履歴・会話等のDB
├── Windowsの実行記録・完成記録
├── 制作ファイル・素材・生成物・チェックポイント
└── 完成を示す記録
```

1. 対象・保存先・必要容量・既知の不足を示す。新しい制作操作と記録更新、待機依頼の着手を止め、実行中の処理を安全な境目で停止する。Windows側の停止・未解決の開始許可を照合する。停止・照合できなければ書き出しを始めない。既存の個別停止契約を使い、新しい作品全体停止機能を追加するものではない。
2. 人間にも、対象の作業用ファイルの保存を済ませ、書き出し中は編集しないよう示す。アプリ外の更新を止められたとは仮定せず、取り込み・コピー時に一貫性を検証する。未登録・未保存のGUI内容までバックアップしたとは表示しない。
3. DBの一貫したスナップショット、Windowsの実行記録、固定実体を未完成の書き出し先へコピーする。開いているSQLiteファイルの単純コピーだけで整合したスナップショットとしない。既存の完成バックアップへ追記・上書きしない。
4. 構成一覧に全対象のID・参照・相対パス・サイズ・ハッシュを記録する。既知の明示削除・不足・破損は理由とともに別記し、実体を含めたものと区別する。予期しないコピー失敗を、成功させるために既知の不足へ読み替えない。
5. DB・参照関係・含めるはずのファイルの存在とハッシュを検証する。成功後に完成を示す記録を確定する。容量不足・中断・コピー失敗・破損時は未完成のままとし、既存の制作データと完成済みバックアップを維持する。
6. 完了／失敗と不足を示して書き込み停止を解除する。停止した依頼は自動再開しない。予期しない終了後も未完成データを完成扱いにせず、照合・再検証する。

同じディスクのフォルダーへ書き出すだけでPC故障への備えが済んだとは扱わない。利用者が指定した保存先へ書き出す機能であり、クラウド同期・保存媒体の管理は含めない。

### Git情報と除外対象

[Git版管理設計](git-versioning.md)に従い、リポジトリ識別・資格情報を含まないGitHubの所在・Gitオブジェクト形式と、参照するフルコミットハッシュ・保持用タグを含める。作品、依頼、成功／失敗の全実行、版切替等の参照を対象とし、採用分だけに絞らない。書き出し時のローカル可用性、リモート保存の最終確認結果・時刻、未push・欠損・確認不能も保持する。

Gitオブジェクト・bundle・実行用の定義キャッシュはGit実体の代替バックアップとして含めない。未pushでも制作データは書き出せるが、そのGit内容を別PCで復旧できるとは表示しない。

資格情報、Codex専用保存領域の内部会話継続データ、接続セッション・実行許可は移行しない。原文・要約・履歴とCodexのthread/turn/itemの対応履歴はDBの制作記録として残すが、対応IDがあるだけで移行先から旧会話を再開しない。ログ・生成スクリプト等も資格情報を保存対象に混ぜない契約とし、保存内容の具体的な検査を実装仕様へ渡す。

## バックアップからの復元・別環境への移行

1. 完成を示す記録と形式識別を検査する。未完成・未対応形式を推測して利用しない。空の保存先を指定し、既存データとのID衝突は合流やIDの振り直しで解消せず、空の保存先を選び直す。
2. 構成一覧、DBの整合性・参照、含まれる実体のサイズ・ハッシュを検証する。相対パスの逸脱・不正なリンク先を拒否する。新しい領域へコピーしてから、復元先でも検証する。
3. 既知の不足が記録されたデータは残存部分を復元できる。書き出せたはずの実体の破損・欠落やDB・構成一覧の不整合は復元失敗として扱い、利用中の保存先へ切り替えない。不足のある正常なバックアップと、破損したバックアップを区別する。
4. 永続ID、理由の訂正履歴、派生・振り返り等の参照を保持し、Windows／WSLの新しいルートを対応付ける。旧PID・世代・開始許可を有効化せず、過去の実行記録として保持する。未完了依頼は照合・手動再開の対象とする。
5. 検証後に復元した保存先を利用可能にする。途中失敗・中断時は未完成領域と元バックアップを保ち、既存環境を上書きしない。再試行でも完成済みデータに重複登録しない。
6. GitHubから必要な保持用タグを明示取得し、コミット・内容を照合する。同名タグの不一致をforceで上書きしない。オフライン・未push・取得失敗はGit未復旧とし、履歴閲覧・手作業の記録を妨げず、欠けた定義・作風が必要な実行だけを止める。バックアップ内の保存確認結果を、移行先での新しい確認結果と混同しない。
7. 移行先のCodex専用領域で別途認証し、新しいCodex会話へ必要な制作記録を渡す。アプリ上の会話原文は読めるが、AI内部の文脈の完全復元は保証しない。文脈の構築は[会話・作風の設計](https://github.com/Kurarowa305/scene-craft/issues/10)で具体化する。Git復旧・認証・起動だけでは制作を自動再開しない。

バックアップ中に停止した依頼以外の未着手・保留依頼も、復元しただけで自動着手しない。作品の制作実体が不足する場合は、その実体が必要な復元・派生・実行を止め、残存データの閲覧・記録は利用できる。

## ローカル保存形式の移行

保存形式の識別とGitの内容の版を分ける。[Git版管理設計の移行契約](git-versioning.md#ローカル保存形式の変更)に従い、変更内容・必要容量・退避先を示し、人間の確認後に書き込みを止める。

変更するDB・ローカル記録・実体を、元の構成とサイズ・ハッシュを持つ退避領域へコピーし、復旧に必要な構成が揃ったことを検証してから変換する。DBだけの変更なら制作実体・Git履歴を一律に複製しない。退避失敗時は変換を始めない。

変換の段階と退避先を永続化し、変換後のID・参照・形式を検証してから利用する。中断・失敗時は変換結果を成功扱いで開かず、退避した元の構成へ戻せる状態を維持する。新旧データを混在させて継続しない。成功後も退避を自動削除しない。移行後の追加記録を失う旧状態への復元は、影響を示した別の明示操作とする。
