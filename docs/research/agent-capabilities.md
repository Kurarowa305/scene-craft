# 背景イラスト制作支援エージェントの公開事例調査

調査日: 2026-10-04。これは候補を比較するための調査資料であり、仕様本文ではない。調査後の利用者による候補の選定結果も記録する。

対象は、一人で Blender と Photoshop を使い、静止画の背景イラストを制作する場面。利用者の「海辺の小さなバス停」の制作記録を評価の前提とする。調査した公開例の数から普及率や「最もよく作られる役割」は判断できないため、以下では公開実装・研究で確認できた役割と、アプリの自動化機能を区別する。実機での品質・互換性検証は行っていない。

## scene-craft への示唆（提案）

以下の推奨度は公開例の人気ではなく、利用者が感じた負担、人が残したい判断、操作の定型化しやすさから評価したもの。高は制作基盤に含めることを強く勧める役割、中は具体的な用途を限定すると役立つ役割、低は現状では専用化する理由が弱い役割とする。実装順序や、一工程だけを先に作るという判断は含まない。役割の区分であり、それぞれを独立したプロセスとして実装する判断も含まない。

| 候補となる役割 | 推奨度 | 対象と理由・人に残す判断 |
| --- | --- | --- |
| 参考調査・検討項目の整理 | 高 | 参考画像の候補と決める項目を整理する。素材検索の実装例はあるが、参考資料の解釈は別の仕事。時間帯・配色・雰囲気の採用は人が決める。 |
| シーン計画・制作要素の分解 | 高 | バス停を土台・梁・屋根・ベンチ・標柱へ分解し、必要な部品と位置関係を整理する。配置計画の研究例がある。画面外の構造や地形は仮説として示し、人が意図に合うか判断する。 |
| 定型モデリング・仮形状作成 | 高 | 屋根の波形、梁、柱、ベンチ等の反復作業に合う。形状操作の実装例がある。大まかな配置と主要なシルエットは人が調整できるようにする。 |
| 植物・小物配置と周囲の整備 | 高 | 制作記録で特に負担が大きい。選んだ素材を対象領域・密度・除外領域に従って配置する案。Geometry Nodes による反復配置が根拠。単なるランダム配置で画面が整うとは限らない。 |
| UV・画像テクスチャ適用 | 高 | 人が画像を選び、AI が UV 展開、向き・縮尺、材質への接続を支援する。自動化 API はあるが、見える面での歪み・継ぎ目確認が必要。 |
| アセット検索・取り込み | 高 | 既存素材で作成を省けるものを提示し、採用後の取り込みを支援する。素材の出典・利用条件も候補と一緒に扱う。最終選択は人が行う。 |
| 空・海・照明の基礎設定 | 高 | 指定した時間帯・天気に合わせた初期設定と調整案を作る。物理設定は出発点であり、画面のために人が変更した IOR・粗さ・光を尊重する。3Dの雲生成も含め、レタッチで描くかは作品ごとに人が判断する。手修正を保護する具体的な仕組みは未確定。 |
| 出力・引き渡し支援 | 高 | 画像と編集用データの保存、出力設定の確認を担う。固定処理で足りる部分は通常の自動化として実装でき、毎回 AI 判断を挟む必要はない。 |
| 画面レビュー | 中 | 採用した意図に対して、配置・見え方・不足を指摘する。レンダー画像による反復の研究例がある。修正の採否は人が決め、写実性を唯一の基準にしない。 |
| Photoshop のレタッチ準備・補助 | 中 | レイヤー整理や指定操作の補助から始める候補。筆致や描き込みの表現は人が主導し、雲をレタッチで描くかは作品ごとに決める。API 対応範囲と必要な操作を実機で確かめる。 |
| 構図・カメラの自動決定 | 低 | 技術的な操作例はあるが、利用者が楽しみ、作品の印象を決めたい工程。人の指示による操作や比較案の補助にとどめる案。 |
| 振り返り・作風の言語化 | 高（要求由来） | 完成した作品と制作履歴を参照して、採用・不採用や手修正の理由から作風の傾向を仮説として言語化する。制作方針への採用は人が決める。今回の公開事例から標準的な機能とは断定できず、利用者固有の要求として評価する。 |

## 調査候補に対する利用者の選定結果

2026-10-04 の要件インタビューで、利用者は推奨度「高」の役割を初期の基盤構築に含めることを選んだ。対象は参考調査、シーン計画、仮形状・定型モデリング、アセット検索・取り込み、周辺整備・植物配置、UV・テクスチャ適用、空・海・照明設定、出力・引き渡し、振り返り・作風の言語化である。一工程だけに絞る方針は採らない。

加えて、3Dの雲生成も対象に含める。元の制作記録で雲をレタッチしたことは、その作品での判断であり、基盤全体の制約に一般化しない。雲を3Dで作るかレタッチで描くかは、作品ごとに選ぶ。上表では空・海・照明設定に含めて記載しているが、独立したエージェントにするかは未確定。

2026-10-05 の要件インタビューで、利用者は次の初期範囲を選んだ。

- 工程の進行管理は将来段階とし、初期は人間が工程ごとのエージェントを選んで呼び出す。作品の制作意図・採用済みの結果・制作履歴は次のエージェントへ引き継ぐ。
- 画面レビューは初期対象に含めない。振り返り・作風の言語化は引き続き初期対象とする。
- Photoshop の支援はレイヤー整理のみを初期対象とする。具体的には名前変更と見た目を維持するグループ化を含み、順序変更・削除・結合、色などの補正、描き込みは含めない。
- 手修正は意味のあるまとまりごとに変更前後と理由を結び付ける。Blender・Photoshop の両方で、人間が「ここまでを一つの修正として記録」と区切りを指定し、前回の記録からの変更をまとめる。理由は短い自由文で入力するか、未入力のまま後から補える。理由をその場で入力できなくても制作は続けられる。既存作品は取り込み時点を最初の記録にする。変更の検出方法は未確定。
- エージェントが変更できる範囲は、人間が触った箇所かどうかではなく、依頼で合意した変更範囲を基準とする。範囲内で編集案を作り、範囲外の変更が必要なら確認する。カメラなどへの明示的な保護指定も設ける。新しい依頼が既存の保護指定と競合した場合、自動で解除せず確認し、人間が変更を明示的に認めた場合に変更する。「今回は変更してよい」という許可はその依頼だけに適用し、次の依頼では保護を維持する。継続的な解除は別途明示する。保護指定の粒度は未確定。
- 編集案は独立して判断できる変更ごとに採用する。例えば植物配置と照明調整は分け、一方が他方に依存する場合はまとめて確認する。
- 編集案を確認中に人間が直接手を加え、「修正して採用」できる。AI が作った状態と人間が直した状態を区別して残す。
- 初期のやり直しは、記録した時点の制作データへ戻る形とし、戻す前の状態も残す。後続の手修正を維持しながら以前の AI 編集だけを選択的に取り消すことは、初期対象に含めない。
- 初期は、エージェントが編集案を作っている間、同じ制作データを人間が同時編集しない運用とする。別作品の制作や参考調査は進められる。完成した編集案への手修正とは区別する。
- エージェント改訂履歴は、各実行と当時の指示・モデル・ツール・手順などの設定、および変更理由を結び付けて追跡できる範囲を初期対象とする。過去の実行環境の完全な復元は含めない。
- 振り返りは、完成した一作品と複数作品を横断した分析の両方を初期対象とする。人間が対象作品を選んで起動し、具体的な作品・採否・手修正を根拠として示す。理由が未入力の箇所は意図を断定せず、仮説として扱う。
- 初期は会話を利用の入口とする。対象作品を明示して依頼し、結果を Blender・Photoshop で確認して、採用や記録を会話で指示する。専用の管理画面は初期対象に含めない。
- 作風もバージョン管理の対象とする。「作風の傾向」と、人間が採用した「制作方針」の区別を維持して扱う。作品で使う作風の版は固定し、人間が選んだときに更新する。
- バージョン管理は Git を正とし、ローカルのデータに独立した版番号を設けない。初期はツール・エージェントの定義と作風の傾向・制作方針を同じリポジトリで管理し、実行にはコミット済みの内容を使う。ローカルの記録にはフルコミットハッシュを保存し、タグは任意の表示名とする。エージェント定義と作風の参照するコミットが異なる場合も、それぞれ Git のハッシュで記録する。
- 制作ファイル本体は初期はローカルに保存し、各記録に使用した定義・作風の Git コミットを残す。作品・実行・保存状態を区別する ID は持つが、独立した版番号としては扱わない。版の判断の理由と未確定の境界は [ADR 0001](../adr/0001-git-authoritative-versioning.md) に記録する。
- 定義や作風の変更内容を人間が採用した後、エージェントが対象の変更をローカルにコミットする。そのコミットを以後の実行で参照し、リモートへの公開は別の操作として扱う。
- 通常の制作に使う変更を main に集約し、ツール・エージェントの追加や修正は feature/*・fix/*、作風の更新は style/* の短命なブランチで進める。変更ブランチのコミットを明示した試行も可能とし、制作データのコピーを使ってコミットと結果を記録する。
- 初期はローカルで人間が変更内容を確認して統合でき、PR は任意とする。検証は一律の必須条件にせず、コミットとマージの前にそれぞれ毎回、実施するか人間に確認する。省略を選んだ場合も進められ、実施有無と実施した場合の結果を記録する。main にあることだけでは検証済みと扱わない。
- 元のコミットを保持するマージを使い、制作履歴から参照済みの履歴は rebase や squash で置き換えない。不採用の実験も、ブランチ削除前に保持用の Git 参照を残す。理由と運用の詳細は [ADR 0002](../adr/0002-short-lived-branches-and-human-validation-choice.md) に記録する。
- 新規作品に加え、制作途中の `.blend`・`.psd` を取り込んで利用を開始できる。取り込み以前の制作過程は不明として扱い、過去の理由は必要に応じて人間が補足できる。
- 過去の保存状態を復元するために必要なテクスチャやリンク素材も保存対象とする。保存できない外部依存がある場合は不足を示し、その保存状態を完全に復元可能とは扱わない。
- 不採用や失敗も含め、会話・採否・理由・失敗内容は記録に残す。大容量の生成物は人間が明示的に削除でき、削除後も記録は残して実体がなく復元できないことを示す。
- 参考調査の成果物は、出典・参考にする要素・制作意図との関係をセットで残す。人間が採用した参考資料を次の工程へ渡す。
- シーン計画では物体の分解、位置関係、おおよその寸法、制作順序まで提案する。参考資料から判断できない構造は仮説として示し、人間が採用してから制作へ進める。
- モデリングは仮形状と、柱・屋根・ベンチなどの定型的な形状作成を初期対象とする。人間が部品ごとに編集できる状態で渡し、作品固有の細かな造形は人間が仕上げる。
- アセット検索は手元の素材ライブラリと外部の素材サービスの両方を対象にする。候補にプレビュー・出典・利用条件を添え、人間が選んだ素材を取り込む。外部サービスの具体的な選定は未確定。
- Photoshop への引き渡しは、合成済み画像に加えて、人間が指定した要素を分けた出力も初期対象とする。分け方は作品ごとに選ぶ。Photoshop 側の支援は、決定済みの名前変更と見た目を維持するグループ化までとする。

上記は調査候補に対する選定・関連判断の記録であり、要件定義の完了や実装方式の確定を意味しない。

## 共通機能として持つことを勧めるもの

制作履歴の記録は、振り返りエージェントを起動したときだけ行うのでは遅い。各工程を個別に使い始める段階から、作品・会話・生成物・編集案・採否・人間の手修正と理由・エージェント改訂履歴の対応を残すことを勧める。これは利用者の要求を満たすための提案であり、公開例に共通する標準仕様という意味ではない。手修正の区切りと理由入力の方針は上記の選定結果に記録した。変更の検出方法は未確定である。

編集案の比較・採用・差し戻しも工程間で共通に扱う候補とする。ファイルの保存や決められた出力手順など、判断の不要な部分は通常の自動処理にできる。エージェントの役割数と、独立した実行プロセスの数を一致させる必要はない。

構図・カメラの自動決定は優先度を低くし、必要なら人が指定した条件で比較案を作る補助として扱う。3Dの雲生成は利用者の選定により対象に含めるが、専用エージェントとして独立させる必要があるかは未確定である。

## 検証すべき境界

- 「定型操作を実行できる」と「今回の画面に適した結果を自律判断できる」を分ける。植物配置、UV、光の調整では、実際の制作データで前後比較が必要。
- 変更範囲と保護指定を基準に編集案を作り、保護指定との競合時は確認する方針が選定済み。独立した変更ごとの採用、修正して採用する方針、記録した時点へのやり直しも選定済み。指定の粒度、変更間の依存関係を見分ける方法、復元に必要なファイルの保存方法は検討が必要。
- 会話ログや Blender / Photoshop の操作履歴だけから、手修正の理由や作風を確定できるとは考えない。人間による区切りの指定と任意の短い理由入力で、必要な記録を無理なく残せるか検証する。作品への紐付け方法は未確定。
- 対象 OS、Blender / Photoshop のバージョン、操作経路、利用する素材サービスは未選定。この調査は特定ツールの導入推奨や動作保証を行わない。
