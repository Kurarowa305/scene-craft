# scene-craft の開発フロー

2026-10-06 に利用者と合意した進め方。mattpocock のスキルを使い、設計項目ごとの資料化を scene-craft の運用として加える。要件整理は完了し、次は設計 Issue を一つずつ解決する段階にある。

## セッションを再開する

1. [初期要件](../requirements/initial-scope.md) と [設計一覧](../design/README.md) を読む。要件整理を最初から繰り返さず、変更要求がある箇所だけ合意を更新する。
2. 設計一覧から親の設計マップ Issue を開き、子 Issue の状態・依存関係を取得する。依存先が完了し、未着手の設計 Issue を選ぶ。利用者が指定した Issue があれば優先する。
3. 選んだ Issue の問い、関連する要件・設計資料・ADR を読み、`wayfinder` に従って作業する。選択前に全 Issue の詳細を読む必要はない。

今回の引き継ぎでは設計 Issue の登録までを行い、調査・試作・設計判断は次のセッションで開始する。登録済みであることは、設計の合意や実装の完了を意味しない。

## スキルと段階

スキルは利用環境のカタログから同名の `SKILL.md` を読み、その指示に従う。この作業環境ではリポジトリの親ディレクトリの `.agents/skills/` に配置されている。進め方に迷ったときは `ask-matt` を参照する。

| 段階 | スキル | 次へ進む条件 |
| --- | --- | --- |
| 要件・変更要求のすり合わせ | `grill-with-docs`（`grilling` + `domain-modeling`） | 必要な問いが解決し、利用者が共有理解を確認した。要件・用語・必要な ADR を反映した |
| 大きな設計の分割・進行 | `wayfinder` | 設計上の問いを子 Issue として管理し、依存先が完了した問いから解決する |
| 設計判断 | `grilling` + `domain-modeling`、モジュール境界には `codebase-design` | 利用者と結論を合意し、根拠・未決事項・後続への影響を記録した |
| 根拠が不足する設計 | `research`、動かして判断する場合は `prototype` | 調査・試作の結果と限界を記録し、元の設計 Issue へ戻した。試作を本実装の完了とは扱わない |
| 実装仕様の統合 | `to-spec` | 決まった要件・設計から実装範囲、受け入れ条件、テスト境界を統合した仕様 Issue を作った |
| 実装への分割 | `to-tickets` | データ・処理・画面を通して動作確認できる単位で分割し、利用者と分割案を確認して依存関係付き Issue を作った |
| 実装 | 原則 `implement` を Issue ごとの新しいコンテキストで使用。まとめて進める運用を選ぶ場合は `implement-spec` | 合意した振る舞いを実装し、`tdd` によるテストと `code-review` による仕様・規約の確認を行った |
| 公開・振り返り | PR を作る場合は `pr`、開発後は `retro` | 変更と確認結果を記録し、開発上の学びを次の作業へ反映した |

実装前の設計が固まるまでは `wayfinder` を使う。設計 Issue を直接実装する扱いにせず、`to-spec` で判断を統合してから `to-tickets` へ進む。13の設計領域を、そのまま13の横割り実装 Issue に変換しない。例えば「作品を作成し、会話を保存して開き直せる」のように、利用者が確認できる振る舞いで分割する。

## 記録の役割

| 記録先 | 正として管理する内容 |
| --- | --- |
| `docs/requirements/initial-scope.md` | 合意済みの初期要件と制約。要件変更を合意したら更新する |
| 設計マップ Issue | 設計の進捗と判断への索引。詳細は子 Issue と資料へリンクする |
| 設計の子 Issue | 問い、選択肢、検討経緯、その時点の結論。閉じた Issue は当時の履歴として残す |
| `docs/design/` | 複数の判断を統合した、現在採用している設計 |
| `docs/adr/` | 後から理由が必要になる重要な選択とトレードオフ。すべての設計を ADR にしない |
| `GLOSSARY.md` | ドメイン用語の定義 |
| `docs/research/` | 調査の根拠・確認範囲・限界。要件や現在の設計本文はそれぞれの資料へリンクする |
| 仕様・実装 Issue | その開発単位の実装範囲・受け入れ条件・進捗。根拠にした要件・設計を参照する |

要件を別の「初期要件 Issue」に全文複製する必要はない。2026-10-06 の合意に従い、要件本文は docs に置く。実装仕様 Issue は開発単位の合意としてまとめ、根拠にした要件・設計資料のコミットをリンクして参照時点を明確にする。設計変更時は現在の設計資料を更新し、影響する未完了の仕様・実装 Issue に変更点を反映する。

## 設計 Issue の完了と資料化

設計 Issue は問いが一セッションで扱える粒度を目安とする。13項目は設計資料の整理単位であり、検討中に問いが大きいと分かった場合は子 Issue を分割して依存関係を張り直す。

1. 利用者と設計の結論を合意する。事実確認・試作の結果と、利用者が選ぶ判断を区別する。
2. 13項目のうち一つの設計がまとまったら、その項目の `docs/design/` 資料を作成・更新する。全13項目の完了を待たない。未決事項があれば未確定と明示し、対応する Issue にリンクする。
3. 資料には責務・構成、データやインターフェース、制約・失敗時の扱い、関連設計との境界、根拠 Issue／ADR を必要に応じて記載する。決まっていない技術選定や値を埋めて完成扱いにしない。
4. 子 Issue に結論の要約と資料・根拠へのリンクを解決コメントとして残して閉じる。資料が main に未統合なら、実際に読めるコミットへのリンクを使う。
5. 親 Issue の Decisions so far に一行の要約と子 Issue へのリンクを追加する。新たな問いは追加し、依存関係と未決事項を更新する。

Issue は当時の判断、設計資料は現在の構成を説明する。過去の議論全文を資料へ転記せず、将来の変更で閉じた Issue の結論を書き換えない。これが `wayfinder` 標準の Issue 中心の記録に追加する、本プロジェクトの運用である。

## Git と検証

ブランチ・統合・検証の運用は [ADR 0002](../adr/0002-short-lived-branches-and-human-validation-choice.md)、制作から参照する版は [ADR 0001](../adr/0001-git-authoritative-versioning.md) に従う。

検証を行うか毎回人間に聞くのは、**初期構築が完了した後にツールや指示を更新するときだけ**である。初期構築中やそれ以外の変更では、この確認を挟まず適切な検証を行う。スキルの一般的なテスト手順より、この合意した適用範囲を優先する。検証の省略を選んだ場合は未検証と明記する。

## セッションを終える

解決した判断、更新した資料、残る問い、次に着手できる Issue が、設計マップと関連 Issue から分かる状態にする。途中で終了する場合は、調査済みの事実・利用者の回答待ち・作業中のブランチや資料を該当 Issue に記録する。別ディレクトリや別の実行環境へ渡す必要がある場合は `handoff` を使う。会話だけに判断を残さない。
