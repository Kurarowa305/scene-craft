# 読めるHTML設計資料

読者が「何を作り、どう動き、何を保証するか」を、HTMLだけで概要から厳密な仕様まで確認できる資料にする。詳細Markdownを正とし、簡潔にする対象は説明の冗長さであり、仕様項目ではない。

## 掲載内容

- ポータルの掲載内容はすべて合意済みとして扱う。合意状況のバッジ・注意書き・進捗や未確定事項の一覧は載せず、未確定情報を探す調査や確認も行わない。
- 入口は「全体像」など内容を示す見出し、構成図、設計一覧を中心にする。宣伝的なタイトル、役割数・レイヤー数等の集計、固定の設計領域数、検索窓は設けない。設計一覧は項目が増えても成立する構成にする。
- 各設計は作る機能と仕様、必要な処理の流れ、契約表、制約・失敗時の動作を説明する。「つながる設計」の章や、設計領域同士のつながりの解説は設けない。製品自体の構成・処理を説明する図は必要に応じて使う。
- 資料の整備記録、Markdownを残しているといった管理上の説明、検証の進捗は本文へ載せない。ポータルのヘッダーに設計マップへのリンクを置かない。
- 現在の仕様はHTML内に掲載する。Markdown・Issueへのリンクは出典・判断根拠・検討経緯の参照に使い、仕様の説明をリンクだけで代替しない。過去の本文スナップショットや資料の移行記録は載せない。製品のデータ移行・復旧手順は仕様として掲載する。

## 文章の書き方

- 本文・表・図の説明は、基本的に「すること」を記載する。採用していない方式、対象外の機能、「しない」「保証しない」の列挙は省く。
- 制約は肯定形の動作・条件へ整理する。例えば「自動再開しない」は「人間の指示で再開する」、「未検証の出力を成功扱いにしない」は「出力の検証後に成功を確定する」と記す。
- 否定文を単純に反転せず、元資料の仕様に沿って、対象・開始条件・確認・保持内容・失敗時の対処を明確にする。採用機能、フィールド、値、状態遷移は維持する。
- 「ログイン時の自動起動を初期の運用にしない」のような対象外の説明は削り、「Windowsのショートカットから起動する」と利用する操作に絞る。

## 情報量と説明の粒度

- 詳細Markdownの現在の設計を、情報を落とさず再構成する。エンティティ、フィールド、API、パラメータ、状態、処理、条件、制約、失敗時の扱いを網羅し、概要だけに要約しない。
- フィールド・APIパラメータは、名前・意味・型・必須／任意・既定値・許容値・制約・参照先など、元資料で定義された情報をすべて掲載する。未定義の名前・型・値を推測して埋めない。論理的な契約を実装済みAPIや物理スキーマとして扱わない。
- 処理は開始条件・入力・実行内容・結果・記録や状態の変化まで示す。分岐条件・全状態遷移・例外・停止・再実行・復旧・整合性を保つ条件も省略しない。
- 数値上限・適用時点・自動処理と人間の判断の境界・失敗後の保持内容と再開条件を明記する。開始条件・検証・停止・再開・保持の具体的な動作として整理する。
- 簡潔さは、重複の統合、短い文章、比較表、図による構造化で実現する。章数・文字数を先に制限せず、仕様項目や条件を削って短くしない。現在の仕様に不要な決定日・承認経緯・検証証跡は出典へ委ねる。
- 読む順序は、目的・全体像から構成・処理へ進み、個別の契約・厳密な定義・例外をたどれる形にする。長いページはページ内目次と節へのリンクを設ける。概要と詳細を別々に重複掲載しない。
- 全体像以外の各設計ページは、タイトルの直下にページ内目次を置く。タイトルと目次の間にキャッチコピー、ページ全体の導入文、概要フローを挟まない。目次は通常幅・モバイル・印刷ですべて縦1列とし、本文の章順に上から下へ並べる。個別の仕様・条件の説明は対応する本文の章へまとめる。
- 図は関係と流れ、表は網羅的な定義、文章は意味・理由・注意点を担う。長文の単純転記や一つの巨大な表への集約を避け、対象・処理・定義ごとに章を分ける。
- 元資料と表の全行・列、列挙項目、値、条件、例外を照合する。除外するのは重複・履歴・証跡・引き継ぎ索引であり、その中に固有の技術契約があれば該当の本文へ統合する。資料間で更新時点が違う場合は、現在採用している設計を参照し、古い選択肢を現行仕様として併記しない。

## 章立てと図表

- 箇条書きの分類名は通常の文字で親項目に置き、具体的な説明・条件を子の `ul` / `li` へ入れてインデントで階層を示す。「分類名：」を太字で本文先頭へ埋め込まず、同じ分類の説明を親項目の下へまとめる。この規則は本文・表セル・カード内の箇条書きへ共通適用する。フロー図の工程名や表・カードの見出しは、それぞれの役割に合う見出し表現を使う。

- ページ内目次のコンポーネント名は「目次」とする。各章の見出しは「1.」、章内の節は「1-1.」の形式で番号を付け、章・節の関係を実際の見出し階層とsectionの入れ子で表す。目次にも同じ番号を付け、節をインデントする。章番号はページ単位で振り直し、既存の参照用IDを維持する。章はh2、節はh3とし、章の見出しは本文幅と画面幅に合う文字サイズにする。
- 同じ項目を繰り返す表は一行へ統合する。対象・場面が異なる場合は大分類の列を追加して区別する。元の条件・箇条書き・リンクを保持し、異なる対象の意味を混ぜない。
- 主要データの契約表など一行の情報量が多い表は、概念・対象ごとのカードへ分ける。カードは画面幅・印刷にかかわらず縦一列に並べる。
- 章内の図表を表・箇条書きで補足するときは、図表と同じ項目名を使い、どのプロセス・ノード・段階への説明かを明確にする。図表の全項目を照合し、説明の抜けや対応先が不明な項目を残さない。
- 構成図などの折線矢印は曲線で角を丸める。線の端点・矢印の向き・所属や参照の意味を維持し、角の前後を短い曲線で接続する。

- 一つの章は一つの主題にする。「技術とプロセス」「提案数と補助モデル」のように独立した主題を接続して一章にせず、それぞれの内容を分ける。「通信とモジュールの責務」「制作ツールと生成Pythonの分担」のように関係・責務・比較自体を説明する見出しは使える。
- 情報量を保って図表へ整理できる内容は図表を優先する。起動関係・処理手順はフロー図、構成・所属は関係図、項目別の仕様・条件・保持内容は表にする。本文は図表の読み方と必要な補足へ絞る。
- 処理・手順・起動順序・状態の進行を示すフロー図は、画面幅や印刷にかかわらず、すべて上から下へ流れる配置にする。分岐先は次の段に並べ、順序を示す矢印は下向きにする。横並びや折り返しで順序を表さない。構成・所属・IDの対応を示す関係図では、関係の意味と向きを維持する。
- 図には手順・起動・参照など矢印の意味を明記する。単なる列挙や独立した不変条件は表で示す。条件・分岐・例外・保存内容も図中または対応する表へ載せる。
- 表のセル内に複数のフィールドや要素を並べるときは、読点で連結せず `ul` / `li` の「・」箇条書きにする。括弧内の条件・任意性・許容値は対応する要素に結び付けて保持する。同じ項目の行はまとめ、対象や場面によって区別する必要がある場合は大分類の列を加える。
- 図表化の前後で元の項目・条件・値・リンクを照合する。章を分けたら目次とページ内リンクを揃える。

## 改修時の再構成

- 表の手順や動作をフロー図へ統合するときは、各条件・記録・停止処理を対応する段階へ移す。複数段階に共通する補足だけを章の後半に箇条書きの注釈としてまとめ、フローの本文と重複させない。障害表の列名は「障害」「扱い」とし、障害欄には対象の名前だけでなく接続切断・連絡途絶・異常終了など具体的な事象を書く。

- 章は利用目的・処理の責務で分ける。保存データの近くに書かれていても、認証・設定・復元を保存処理の章へ混在させない。概要ページでは主要な構成・処理を先に置き、少量の補助的な話題は後半へまとめ、必要な契約をカード内に残して詳細ページへリンクする。

- 修正指示を末尾へ単純に追記せず、ページ全体の読む順序を見直す。全体像・関係図・契約・具体例・制約の役割を整理し、必要なら章立てや既存説明を更新して重複を除く。
- 共通ルールはこのスキルへ反映する。ページ名を変更するときはタイトル・見出し・共通ナビゲーション・入口のカードを揃える。
- エンティティの契約は元資料の全エンティティを一つずつ対応させ、複数概念をまとめて省略しない。情報量が多い場合は一エンティティ一カードに分け、必ず縦一列に並べる。必須・任意・条件付き情報と責務をラベルで区別し、元のフィールド・条件を保持する。図とカードの名前・対象範囲を揃える。
- 元資料にある関係図を使う際は所属・参照・処理順・システム間の対応を区別し、矢印の向きと省略範囲を維持する。所属関係図と履歴の具体例は分けて説明する。

## 表示と導線

- 表は本文と独立した文字サイズ・行間・列幅を設定する。長い識別子を折り返し、通常幅・実際のモバイル表示・印刷で文字の自動拡大と列のはみ出しを確認する。
- 図は矢印の意味と対象範囲を添え、図の要点を本文でも説明する。表は列の意味を揃え、技術名・値・採否は元の設計内容と一致させる。
- 見出しの階層、読みやすい本文幅と行間、キーボードのフォーカス表示を設ける。狭い画面はナビゲーションと本文を縦に並べ、横長の図表だけを個別にスクロールさせる。
- 設計カードはカード全体を一つの通常のリンクにする。見出し・本文・余白のどこを押しても対応ページへ進め、リンクの入れ子やJavaScript必須の遷移を避ける。
- ポータル内のページは同じタブで開く。GitHub等の外部リンクには `target="_blank" rel="noopener noreferrer"` を付け、別タブで開く。
- 既存の意匠を継承し、静的HTMLとCSSで読める構成を優先する。不要になったJavaScriptと導線を残さない。

## 表示・操作の確認

実ブラウザで通常幅・狭い幅、図表、印刷、キーボード移動を確認する。各カードは見出し以外の本文・余白も実際にクリックし、遷移先を確認する。外部リンクの別タブ動作、ポータル内リンクとファイル参照も確認する。元資料との網羅性・値・条件の一致も確認する。この確認は資料の表示・操作と転記の正確さを対象とし、設計の未確定事項を調べる工程にはしない。

scene-craftの入口は `docs/design/index.html`。テスト・診断・受け入れ設計はポータルの掲載対象に含めない。詳細設計のMarkdownは引き続き維持し、HTMLを更新するときも削除しない。設計内容を変える場合は、既存資料との内容を揃える。
