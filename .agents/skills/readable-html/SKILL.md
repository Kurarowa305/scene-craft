# 読めるHTML設計資料

読者が「何を作り、どう動き、何を保証するか」を、HTMLだけで概要から厳密な仕様まで確認できる資料にする。詳細Markdownを正とし、簡潔にする対象は説明の冗長さであり、仕様項目ではない。

## 掲載内容

- ポータルの掲載内容はすべて合意済みとして扱う。合意状況のバッジ・注意書き・進捗や未確定事項の一覧は載せず、未確定情報を探す調査や確認も行わない。
- 入口は「全体像」など内容を示す見出し、構成図、設計一覧を中心にする。宣伝的なタイトル、役割数・レイヤー数等の集計、固定の設計領域数、検索窓は設けない。設計一覧は項目が増えても成立する構成にする。
- 各設計は作る機能と仕様、必要な処理の流れ、契約表、制約・失敗時の動作を説明する。「つながる設計」の章や、設計領域同士のつながりの解説は設けない。製品自体の構成・処理を説明する図は必要に応じて使う。
- 資料の整備記録、Markdownを残しているといった管理上の説明、検証の進捗は本文へ載せない。ポータルのヘッダーに設計マップへのリンクを置かない。
- 現在の仕様はHTML内に掲載する。Markdown・Issueへのリンクは出典・判断根拠・検討経緯の参照に使い、仕様の説明をリンクだけで代替しない。過去の本文スナップショットや資料の移行記録は載せない。製品のデータ移行・復旧手順は仕様として掲載する。

## 情報量と説明の粒度

- 詳細Markdownの現在の設計を、情報を落とさず再構成する。エンティティ、フィールド、API、パラメータ、状態、処理、条件、制約、失敗時の扱いを網羅し、概要だけに要約しない。
- フィールド・APIパラメータは、名前・意味・型・必須／任意・既定値・許容値・制約・参照先など、元資料で定義された情報をすべて掲載する。未定義の名前・型・値を推測して埋めない。論理的な契約を実装済みAPIや物理スキーマとして扱わない。
- 処理は開始条件・入力・実行内容・結果・記録や状態の変化まで示す。分岐条件・全状態遷移・例外・停止・再実行・復旧・整合性を保つ条件も省略しない。
- 数値上限・適用時点・自動処理と人間の判断の境界・失敗後の保持内容と再開条件を明記する。元資料の「対象外」「保証しない」も契約の一部として残す。
- 簡潔さは、重複の統合、短い文章、比較表、図による構造化で実現する。章数・文字数を先に制限せず、仕様項目や条件を削って短くしない。現在の仕様に不要な決定日・承認経緯・検証証跡は出典へ委ねる。
- 読む順序は、目的・全体像から構成・処理へ進み、個別の契約・厳密な定義・例外をたどれる形にする。長いページはページ内目次と節へのリンクを設ける。概要と詳細を別々に重複掲載しない。
- 図は関係と流れ、表は網羅的な定義、文章は意味・理由・注意点を担う。長文の単純転記や一つの巨大な表への集約を避け、対象・処理・定義ごとに章を分ける。
- 元資料と表の全行・列、列挙項目、値、条件、例外を照合する。除外するのは重複・履歴・証跡・引き継ぎ索引であり、その中に固有の技術契約があれば該当の本文へ統合する。資料間で更新時点が違う場合は、現在採用している設計を参照し、古い選択肢を現行仕様として併記しない。

## 改修時の再構成

- 修正指示を末尾へ単純に追記せず、ページ全体の読む順序を見直す。全体像・関係図・契約・具体例・制約の役割を整理し、必要なら章立てや既存説明を更新して重複を除く。
- 共通ルールはこのスキルへ反映する。ページ名を変更するときはタイトル・見出し・共通ナビゲーション・入口のカードを揃える。
- エンティティの契約表は元資料の全エンティティを一行ずつ対応させ、複数概念をまとめて省略しない。図と表の名前・対象範囲を揃える。
- 元資料にある関係図を使う際は所属・参照・処理順・システム間の対応を区別し、矢印の向きと省略範囲を維持する。所属関係図と履歴の具体例は分けて説明する。

## 表示と導線

- 図は矢印の意味と対象範囲を添え、図の要点を本文でも説明する。表は列の意味を揃え、技術名・値・採否は元の設計内容と一致させる。
- 見出しの階層、読みやすい本文幅と行間、キーボードのフォーカス表示を設ける。狭い画面はナビゲーションと本文を縦に並べ、横長の図表だけを個別にスクロールさせる。
- 設計カードはカード全体を一つの通常のリンクにする。見出し・本文・余白のどこを押しても対応ページへ進め、リンクの入れ子やJavaScript必須の遷移を避ける。
- ポータル内のページは同じタブで開く。GitHub等の外部リンクには `target="_blank" rel="noopener noreferrer"` を付け、別タブで開く。
- 既存の意匠を継承し、静的HTMLとCSSで読める構成を優先する。不要になったJavaScriptと導線を残さない。

## 表示・操作の確認

実ブラウザで通常幅・狭い幅、図表、印刷、キーボード移動を確認する。各カードは見出し以外の本文・余白も実際にクリックし、遷移先を確認する。外部リンクの別タブ動作、ポータル内リンクとファイル参照も確認する。元資料との網羅性・値・条件の一致も確認する。この確認は資料の表示・操作と転記の正確さを対象とし、設計の未確定事項を調べる工程にはしない。

scene-craftの入口は `docs/design/index.html`。テスト・診断・受け入れ設計はポータルの掲載対象に含めない。詳細設計のMarkdownは引き続き維持し、HTMLを更新するときも削除しない。設計内容を変える場合は、既存資料との内容を揃える。
