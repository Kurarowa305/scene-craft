# 読めるHTML資料

読者が「何を作るか」「どうつながるか」「何が未確定か」を把握し、必要な根拠へ進める資料を作る。

## 構成を決める

- 既存資料・Issueの合意を読み、扱う領域、主要契約、失敗時の扱い、未決事項の所在を対応付ける。設計合意と実装・実機検証の状態を別々に表示する。
- 入口には目的と全体図、領域への短い案内を置く。領域ごとの本文は結論、流れや関係図、比較できる契約表、制約、関連領域と詳細根拠を中心に再構成する。
- 既存の長文をHTMLへ変換しただけで完成としない。細かな引数や検討経緯は承認された正本へリンクし、人間が判断するのに必要な説明を本文へ残す。
- 資料を移行・削除する依頼では、詳細が移行先から取得できることを確認してから削除し、現行の入口と相対リンクを更新する。削除や外部公開の範囲は依頼とリポジトリの運用に従う。

## 読める形にする

- 図は矢印の意味と対象範囲を添える。流れには順序、関係図には関係の種類を示し、例示を完全な状態機械や物理スキーマと誤認させない。図の要点は本文でも説明する。
- 表は列の意味を揃える。色だけで確定・未確定を伝えず文字も付ける。技術名・値・採否は根拠と照合する。
- 見出しの階層、十分な行間、読みやすい本文幅、キーボードのフォーカス表示を設ける。狭い画面ではナビゲーションと本文を縦に並べ、横長の図表だけを個別にスクロールさせる。
- 更新先に既存の意匠があれば継承する。静的資料は外部CDNやビルドなしでも読める構成を優先し、操作が必要な箇所にだけJavaScriptを使う。
- 全領域への入口、詳細Issue・合意コメントへの参照、隣接領域へのリンクを用意する。GitHubのHTMLソース表示とブラウザ表示の違いを入口で説明する。

## 確認して渡す

- 元資料の各内容が本文の要点またはリンク先の詳細に保持されているか照合する。リンク先に旧ファイルへの参照しかない場合は補完し、取得して確認する。
- HTMLのローカルリンク・フラグメント、外部のIssueや合意コメント、見出し・図のラベルを検査する。過去資料の固定コミットリンクは履歴として区別する。
- 実ブラウザで通常幅と狭い幅、キーボード操作、ナビゲーション、図表、印刷表示を確認する。検索等があれば未一致・解除とJavaScript無効時も確認する。
- 確認できた範囲と残る制約、直接開けるHTMLの場所を示す。

scene-craftでは既存Markdownをすべて残し、`docs/design/index.html`を人間向けの入口として併設する。現在の詳細設計は既存Markdown、合意と経緯は設計Issueを参照し、各領域から両方へリンクする。設計変更は開発フローに従って合意・記録し、Markdownとポータルの要点を揃えて更新する。
